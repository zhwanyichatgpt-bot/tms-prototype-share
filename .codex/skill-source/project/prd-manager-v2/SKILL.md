# PRD Manager V2

在可控的上下文和工具往返内，生成业务事实可靠、容易审阅、能够继续支撑原型、研发和标注的 PRD。

## 核心目标

1. 先建立可追溯事实和核心结构，再写正文。
2. 同时保证覆盖完整、逻辑可读和下游可执行，不以填满模板代表质量。
3. 默认由当前智能体一次完成读取、写作和审查，不复制上下文给多个智能体。
4. 关键条件、状态流转、多对象结果和异常边界必须能被快速发现。
5. 保持第 3、4、5、7 章的下游契约，并明确提供原型标注需要的规则信息。

## 不做什么

- 不代替 `discussion` 梳理仍有 P0 分歧的需求。
- 不生成原型、页面代码、原型标注或测试用例。
- 不默认生成流程图、对象图、状态图或 Word 文件。
- 不把当前代码或原型的实现状态自动升级为正式需求。
- 不为补齐模板编造字段限制、提示文案、异常、性能指标或并发规则。
- 不用篇幅、章节数、表格数或审查轮次代表质量。

## 成本与执行硬边界

### 标准模式默认约束

- 使用当前单智能体，不启动 analyzer、writer、reviewer 多轮流水线。
- 先列出直接相关来源，再做一次有效批量读取；同一来源不重复加载。
- 不扫描整个仓库，不读取与当前主题无直接关系的 PRD、规则或原型。
- 只形成一个紧凑事实包，不复制来源长段落。
- 正文通常最多三次文件写入：创建正文、一次局部修正、追加变更记录。
- 只做一次综合语义审查；事实、状态、异常、可测试性和阅读体验在同一轮完成。
- 确定性校验最多运行两次：首次校验、针对失败项修正后的复验。
- 普通生成目标为约 4—6 次必要本地工具操作；需要扩大来源或增加独立审查时先说明成本并获得确认。

### 禁止的高消耗模式

- 不按章节重复读取同一来源。
- 不逐章展示并刷新任务清单。
- 不设置每次写入 80 行或 150 行的机械限制。
- 不因两个局部问题整章重写。
- 不在修正后重新生成全文或无限循环审查。
- 不把完整历史、事实包和 PRD 复制给多个子智能体。

## PRD 生命周期

PRD 不是只在原型完成后补写，也不是讨论尚未收口时提前固化。

```text
讨论记录
  → P0 方向问题收口
  → 初版 PRD（草稿 / 待原型验证）
  → 原型验证
  → 用户认可差异
  → 同一份 PRD 原地更新（待评审 / 已确认）
  → 作为研发和原型标注的正式依据
```

- 初版生成门槛：定位、范围、角色、页面或入口关系、主流程、核心对象关系、自动与人工边界没有 P0 歧义。
- 非阻塞细节可以进入待确认，不要求讨论完所有字段和文案才生成初版。
- 原型只能证明已实现行为；只有用户明确认可的原型差异才能反哺 PRD。
- 同主题维护同一个文件，通过文档状态和变更记录体现阶段，不为每次原型调整新建文件。

建议状态：`草稿 → 待原型验证 → 原型验证中 → 待评审 → 已确认`。

## 工作模式

| 用户目标 | 主模式 |
|---|---|
| 从讨论记录或需求材料创建初版 PRD | 生成模式 |
| 修改某章、补充字段、修正规则 | 局部更新模式 |
| 检查现有 PRD 的业务正确性和完整性 | 审查模式 |
| 把用户认可的原型变化同步到同一份 PRD | 原型反哺模式 |

一次只选择一个主模式。配图、Word、测试用例和标注不属于本 Skill 的默认流程。

## 复杂度选择

### 快速模式

适合单页、小功能、局部章节更新或来源已经高度结构化的需求。

- 精简事实包。
- 使用 `references/prd-template-lite.md`。
- 一次写入、一次综合审查、一次确定性校验。

### 标准模式（默认）

适合一般 0→1 PRD 和多数常规业务功能。

- 完整事实包和核心结构检查门。
- 使用 `references/prd-template-lite.md`，按实际业务深度展开。
- 一次正文、一次综合审查、一次最小修正、一次确定性校验。

### 深度模式

适合监管、财税、结算、跨系统、多应用、来源明显冲突或复杂状态补偿。

- 开始前说明必要性、消耗等级和低成本替代方案，等待用户确认。
- 使用 `references/prd-template-full.md` 的相关扩展，不加载无关扩展。
- 最多调用一次 `agents/prd-reviewer.md` 所定义的独立证据审查。
- 独立审查必须同时获得紧凑事实包和 PRD，不允许只看正文格式。

## 执行流程

### 第一步：加载项目约定

1. 读取项目根目录 `AGENTS.md` 中的 PM 工作流配置。
2. 获取讨论记录、PRD、业务规则和原型目录。
3. 配置缺失时使用：`discussions/`、`prd/`、`context/business-rules/`、`prototype/`。
4. 查找同主题 PRD；同主题默认原地更新，不创建 v3、v4 等碎片版本。
5. 不读取 `CLAUDE.md` 或 `.claude/skills/` 作为 Codex 默认配置。

### 第二步：确定最小来源范围

按权威性列出候选来源：

1. 用户本轮明确确认。
2. 正式业务规则或已确认讨论结论。
3. 同主题已有 PRD。
4. 用户明确认可的原型验证结论。
5. 当前原型或代码，仅用于核对已实现事实。
6. 历史聊天、示例和 Mock 只辅助理解，不能单独形成正式规则。

只读取与本主题直接相关的文件或章节。大文件先定位标题和相关片段；只有规则分散或上下文不足时才扩大读取范围。

### 第三步：形成事实包

读取 `references/evidence-pack.md`，在当前上下文形成一个紧凑事实包。

要求：

- 每条事实标记“已确认、倾向、待确认、明确排除”。
- 记录来源路径和可定位位置，不复制来源长段落。
- 同时整理角色视角流程、对象状态、状态允许操作、事件触发结果和跨对象影响。
- 对时间、数值、权限、重复提交、并发和下游失败只提出来源支持的问题，不自行设计答案。
- 对冲突来源列出冲突，不自行选择有利结论。
- 事实包默认不写入项目；用户明确要求保存时才沉淀。

### 第四步：核心结构检查门

写正文前确认以下项目没有 P0 歧义：

1. 功能定位与业务目标。
2. 本期范围和明确排除项。
3. 角色、数据范围和主要场景。
4. 应用、页面、入口或层级关系。
5. 主流程、关键分支和自动/人工边界。
6. 核心对象、数量关系和主要状态。
7. 对状态型业务，主要事件如何改变相关对象。
8. 来源之间是否存在会改变产品方向的冲突。

材料明确时直接继续，不重复询问。存在 P0 歧义时只问一个最关键问题；用户回答前不生成长正文。P1/P2 问题进入待确认或后续审查。

### 第五步：生成或更新正文

一次批量读取本模式需要的模板和 `references/quality-checklist.md`，不要在每章重复读取。

#### 生成模式

1. 根据复杂度选择精简模板或相关深度扩展。
2. 事实包是正文唯一业务依据。
3. 一次生成第 0—8 章完整草稿并写入目标文件。
4. 先呈现快速理解层，再展开业务执行逻辑，最后提供字段、枚举和追溯信息。
5. 条件分支、状态变化、不可逆操作和异常边界不得埋在长段落中。
6. 没有来源的可选内容省略；影响实现的未知项进入待确认。

#### 局部更新模式

1. 只读取目标章节、直接相关事实和必要的上下文章节。
2. 先判断受影响章节，不默认整章重写。
3. 同步检查状态、规则、功能和字段的关联章节。
4. 只修改受影响内容并追加变更记录。

#### 审查模式

1. 同时读取 PRD 与直接来源或已有事实包。
2. 按质量清单报告 P0/P1/P2，不自动重写。
3. 用户要求修复时执行最小修改；只有产品结构或主流程整体失效才重写相关逻辑块。

#### 原型反哺模式

1. 仅在用户确认原型已经验证认可后执行。
2. 路由或入口注册表只能证明“已实现”，不能证明未注册需求应删除。
3. 每项能力标记：规划中、已实现、已移除、无法判断。
4. 生成逐章差异清单；删除、降级或改变范围前获得用户确认。
5. 只回写用户认可的差异，不把临时页面实现整体抄入 PRD。

### 第六步：一次综合语义审查

按 `references/quality-checklist.md` 在同一轮完成：

1. 事实真实性与确认态。
2. 范围、流程、对象和自动/人工边界。
3. 状态—事件—操作—结果及多对象联动。
4. 时间、数值、权限、并发、重复提交、失败与不可逆边界。
5. 第 2、3、4、5、7 章跨章节一致性。
6. 原型和标注需要的条件、阻断、结果与下游影响是否清楚。
7. 关键结论是否前置，IF/THEN/例外是否容易发现，是否存在重复和密集长段。

审查必须对照事实包。测试思维只用于暴露需求缺口，不生成测试用例，也不把推测写成规则。

### 第七步：一次最小修正

- P0：阻断交付，修正方向错误或向用户确认。
- P1：局部补充、修正，或把无来源内容转为待确认。
- P2：只做必要的表达和维护性调整。

一次修正后不重新生成全文。只有结构整体错误时才重写相关逻辑块，不以问题数量决定重写范围。

### 第八步：确定性校验

运行：

```bash
node {SKILL_PATH}/scripts/validate-prd.mjs {PRD_FILE}
```

脚本只检查结构、frontmatter、重复标题与规则编号、占位符、正文待确认表述和常见技术词。它不能代替业务语义审查。

校验失败时只修复对应问题并复验一次。仍失败则报告具体阻塞，不循环修改。

## 正文编写原则

- 先结论后细节，一个段落只表达一个业务主题。
- 正常流程使用有序列表，并列条件和约束使用无序列表。
- 状态—事件—操作—结果使用表格；复杂业务同时说明多个对象如何变化。
- 关键条件规则使用“适用场景 / 如果 / 则 / 否则或例外 / 提示 / 影响”结构，缺少的无关项可省略。
- 提示文案放在对应条件或阻断规则旁边，不集中堆放。
- 表格只用于固定维度对照；长解释改用短段落或列表。
- 同一规则只在最适合的章节完整说明，其他章节引用规则编号或简述影响。
- 阅读体验来自业务层次和条件清晰，不靠视觉装饰、套话和重复总结。

## 下游契约

### 原型与研发

- 第 3 章：核心对象、状态、进入退出条件、允许操作和多对象联动。
- 第 4 章：可执行规则、条件、结果、例外、提示和影响。
- 第 5 章：角色、入口、正常流程、权限、操作结果和真实存在的异常。
- 第 7 章：表单、列表、详情字段、枚举、可见与可编辑条件。

### 原型标注

PRD 应能直接提供：

- 字段口径、来源、计算和联动。
- 状态与可用操作映射。
- 按钮显示、隐藏、禁用和提交条件。
- 校验与阻断结果。
- 操作后的状态、关联对象和下游单据。
- 异常、并发、不可逆和权限边界中已经确认的部分。

本 Skill 只保证输入契约，不修改或自动触发 `annotation` Skill。

## 文件与版本

```text
{prd_dir}/{模块名}_{主题名}_PRD_v1.md
```

- v1：首次形成。
- v2：核心逻辑发生重大变化，需要重新评审。
- v2 之后的细节调整原地更新，通过状态和变更记录追踪。
- 同主题已有文件时优先更新，不重复创建。

## 完成标准

交付前确认：

- 核心结构检查门通过。
- 确定性结论可追溯到来源。
- 待确认没有写成正式规则。
- 状态、操作、结果和异常边界足以支撑研发判断。
- 第 3、4、5、7 章能够支撑原型和后续标注。
- 已完成一次综合审查和一次确定性校验。
- 告知用户产物路径、文档阶段、P0/P1/P2 处理结果、仍待确认事项和本次未执行的可选能力。

完成后只提示下一步，不自动生成原型、标注、图表、Word或测试用例。

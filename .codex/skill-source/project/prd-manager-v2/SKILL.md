# PRD Manager V2

用更少的上下文往返生成业务逻辑可靠、可供原型和研发继续使用的 PRD。

## 核心目标

1. 先确认业务事实和核心结构，再写长文档。
2. 默认由当前智能体完成，不启动子智能体。
3. 同一来源只做一次有效读取，不在各章节重复加载。
4. 审查业务正确性优先于章节格式。
5. 保持第 3、4、5、7 章的下游契约，兼容原型生成与标注。

## 不做什么

- 不代替 `discussion` 梳理尚未收口的需求。
- 不生成原型、页面代码或原型标注。
- 不默认生成流程图、对象图、状态图或 Word 文件。
- 不用篇幅、标题数量或表格数量代表质量。
- 不因原型尚未实现就自动删除规划需求。

## 默认执行边界

- 默认使用当前单智能体。
- 不继承或复制完整历史给其他智能体。
- 只有用户明确批准高消耗“深度模式”时，才可增加一次独立审查；独立审查必须同时获得事实包和 PRD，不能只看正文。
- 不重复展示逐章任务清单，只在开始、遇到阻塞和完成时汇报。
- 不设置每次写入 80 行或 150 行之类的机械限制；按完整逻辑块写入。
- 完整生成通常最多三次文件写入：创建正文、局部修正、追加变更记录。

## 三种复杂度

### 快速模式

适合单页、小功能、局部章节更新或材料已经非常完整的需求。

- 生成精简事实包。
- 使用 `references/prd-template-lite.md`。
- 一次写入，一次确定性检查。
- 不启动独立审查。

### 标准模式（默认）

适合一般的 0→1 PRD。

- 形成完整事实包。
- 通过核心结构检查门。
- 使用 `references/prd-template-lite.md`；确有复杂内容时按需补充，不机械扩写。
- 一次生成正文，一次语义检查，一次最小修正。

### 深度模式

适合监管接口、跨系统、多个应用或来源冲突明显的需求。

- 开始前说明必要性、消耗等级和低成本替代方案，等待用户确认。
- 使用 `references/prd-template-full.md`。
- 可调用一次 `agents/prd-reviewer.md` 所定义的证据审查。
- 不允许 analyzer、writer、reviewer 多轮循环。

## 模式识别

| 用户目标 | 工作模式 |
|---|---|
| 从讨论记录或材料创建新 PRD | 生成模式 |
| 修改某章、补充字段、修正规则 | 局部更新模式 |
| 检查现有 PRD 是否正确完整 | 审查模式 |
| 把用户认可的原型改动同步到 PRD | 原型反哺模式 |

只选择一个主模式。配图和 Word 导出不属于本技能默认流程。

## 第一步：加载项目约定

1. 读取项目根目录 `AGENTS.md` 中的 PM 工作流配置。
2. 获取讨论记录目录、PRD 目录、业务规则目录和原型目录。
3. 配置缺失时使用：`discussions/`、`prd/`、`context/business-rules/`、`prototype/`。
4. 查找同主题 PRD；同主题默认原地更新，不创建 v3、v4 等碎片版本。

不要读取 `CLAUDE.md` 或 `.claude/skills/` 作为 Codex 默认配置。

## 第二步：确定来源范围

先列出候选来源，只读取与本主题直接相关的内容：

1. 用户明确指定的讨论记录或需求文件。
2. 同主题已有 PRD。
3. 与本主题直接相关的业务规则。
4. 用户明确认可的原型或验证结论。

不要为了“可能有用”扫描整个仓库。大文件先查看目录、标题或相关片段，再决定是否需要完整读取。

## 第三步：形成事实包

按照 `references/evidence-pack.md` 在当前上下文中形成内部事实包。

要求：

- 每条核心结论标记为“已确认、倾向、待确认、明确排除”之一。
- 记录来源路径和可定位位置，不复制整段原文。
- 对冲突来源列出冲突，不自行选择有利结论。
- 事实包默认不写入项目文件；用户明确要求保存时才沉淀。
- 控制在足以支撑 PRD 的最小规模，不重复列出同一事实。

## 第四步：核心结构检查门

写正文前必须确认以下项目没有 P0 歧义：

1. 产品或功能的一句话定位。
2. 本期范围与明确排除项。
3. 用户角色和主要使用场景。
4. 应用、页面或层级关系。
5. 主流程与关键分支。
6. 核心对象、关系和主要状态。
7. 自动处理与人工操作的边界。
8. 来源之间是否存在互相冲突的结论。

如果材料已经明确，直接继续，不重复询问。

如果存在会改变产品方向的 P0 歧义，只问一个最关键的问题；在用户回答前不生成长正文。非阻塞的技术口径进入第 8 章待确认事项。

## 第五步：生成 PRD

### 生成模式

1. 根据复杂度选择精简或完整模板。
2. 使用事实包作为正文唯一业务依据。
3. 一次生成第 0—8 章的完整草稿并写入目标文件。
4. 不为填满模板编造错误提示、字符限制、异常规则或状态。
5. 没有信息的可选小节直接省略；关键字段未知时明确标记待确认。

### 局部更新模式

1. 只读取目标章节、相关事实来源和必要的上下文章节。
2. 先说明本次修改影响哪些章节。
3. 只修改受影响内容；避免整章重写。
4. 追加一条变更记录。

### 审查模式

1. 同时读取 PRD 与其来源材料或已有事实包。
2. 按 `references/quality-checklist.md` 检查。
3. 先报告 P0/P1/P2，不自动重写。
4. 用户要求修复时，执行最小修改；只有结构整体失效才整章重写。

### 原型反哺模式

1. 仅在用户确认原型已验证认可后执行。
2. 路由或入口注册表只能证明“已实现”，不能证明“未注册的需求应删除”。
3. 对每项能力标记：规划中、已实现、已移除、无法判断。
4. 生成逐章差异清单。
5. 删除、降级或改变需求范围前必须获得用户确认。

## 第六步：一次语义检查

对照事实包检查：

- 产品定位、页面结构和主流程是否一致。
- 自动与人工边界是否一致。
- 已确认、倾向和待确认是否混淆。
- 是否出现没有来源的规则、字段或异常处理。
- 第 3、4、5、7 章是否互相一致。
- 功能范围是否遗漏或擅自扩大。

发现问题时进行一次最小范围修正，不重复生成全文。

## 第七步：确定性校验

运行：

```bash
node {SKILL_PATH}/scripts/validate-prd.mjs {PRD_FILE}
```

该脚本只检查结构、重复标题、占位符、正文中的待确认表述和常见技术词。它不能代替业务语义检查。

校验失败时只修复对应问题并重新运行一次。不要启动无限校验循环。

## PRD 下游契约

以下内容必须清晰，供原型技能读取：

- 第 3 章：核心对象、关系和状态。
- 第 4 章：可执行的业务规则。
- 第 5 章：功能、操作、权限、正常与真实存在的异常流程。
- 第 7 章：表单、列表、详情需要的字段与枚举。

其他章节用于理解和追溯，可以精简，但不得与上述四章冲突。

## 文件与版本

```text
{prd_dir}/{模块名}_{主题名}_PRD_v1.md
```

- v1：首次形成。
- v2：核心逻辑发生重大变化，需要重新评审。
- v2 之后的细节调整原地更新，通过变更记录追踪。
- 同主题已有文件时优先更新，不重复创建。

## 完成标准

交付前确认：

- 核心结构检查门已通过。
- 正文中的确定性结论能追溯到来源。
- 待确认事项没有被写成正式规则。
- 第 3、4、5、7 章能够支撑原型继续工作。
- 确定性校验已经运行一次。
- 告知用户产物路径、仍待确认事项和本次未执行的可选能力。

完成后只提示下一步，不自动生成原型、标注、图表或 Word。

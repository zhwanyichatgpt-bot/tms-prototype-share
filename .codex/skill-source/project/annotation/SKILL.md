# 原型标注

## 产品与目录上下文

首次进入本项目新主题或写入阶段，先读取 `context/project-rules/产品架构与目录治理规范.md`，锁定 productId 或 operationAppId、使用端、scope/projectId 和版本。下文的 prd/、discussions/、prototype/ 等均为资产根目录，实际落点必须展开产品/端与项目层级；不得继续向历史平铺目录写入。共用端不复制进各产品；同主题续接不重复读取。


## 目标

让研发在当前界面直接看懂字段口径、业务规则、交互条件和处理结果，同时避免标注点密集、顺序混乱、底层标注穿透和大段文字难读。

标注与 UI 组件库解耦：业务代码只注入全局唯一的 `.annot-*` class；自定义浮层通过统一 `data-annotation-*` 属性接入。

## TMS 版本上下文前置门

分析或写入标注前必须明确：

```text
需求归属：common / project
所属项目：null / projectId
研发版本：pending / versionId
当前修订：pending / R0 / R1 ...
版本状态：进行中 / 已完成
目标页面：pageKey 与真实路由
```

- 归属或项目不明确时不得生成标注。
- 证据优先级为：当前研发版本 → 当前定制项目基线 → TMS 通用基线。
- “发布研发地址”与“标记完成”相互独立；已完成版本的标注仍可继续修改和再次发布。
- 本期不在标注数据中增加“本次变更”、未读或修订差异特殊提醒；这些信息由版本修改记录承载。

## 证据边界

按以下顺序建立最小证据包：

1. 当前研发版本明确纳入的相关依据。
2. 当前归属目录中与目标页面直接相关的 PRD 和业务规则；定制需求可在必要时继续读取其声明继承的通用基线。
3. 路由配置、目标页面和它实际打开的子组件。
4. 本 Skill 的 [标注规范](references/annotation-spec.md)。

不读取其他项目目录或外部商业知识库。不要为了“完整”扫描全部 PRD；先按页面名称、路由、业务对象精准检索。

PRD 决定“应该做什么”，实际页面决定“标在哪里、当前实现是什么”。两者不一致时：

- 标注写经过 PRD 和业务规则确认的目标规则；
- 在交付结果中单独报告页面差异；
- 不擅自修改 PRD或业务页面。

## 版本标注同步模式

当用户说明 PRD、业务规则或原型已经修改，并要求检查、同步或更新标注时，只审查当前研发版本受影响的页面，不重新生成全项目标注。

同步时对照三层证据：

1. PRD / 业务规则差异：确认目标业务规则发生了什么变化。
2. 原型及交互差异：确认页面实际展示、校验、操作和结果是否已经实现。
3. 当前版本标注：判断现有内容应保持、修改、新增、合并或删除。

人工维护标注时可以使用以下判断；按钮同步只输出并写入“修改 / 新增 / 合并 / 删除”，不输出“保持”，冲突单独阻断整批写入：

| 结论 | 使用条件 |
|---|---|
| 保持 | 证据变化不影响该标注表达的业务主题 |
| 修改 | 同一主题的规则、字段口径、状态、操作或结果已经变化 |
| 新增 | 出现研发必须知道且现有标注没有覆盖的独立主题 |
| 合并 | 相邻标注开始重复，或可以在一个稳定区域中连续阅读 |
| 删除 | 规则取消、宿主消失、内容可由界面直接理解或不再具有研发价值 |
| 冲突 | PRD、规则和原型相互不一致，无法确认目标口径 |

- 发生冲突时停止该项写入并报告，不以某一份证据覆盖其他证据。
- 当前版本的版本化标注是交付依据；不得把项目定制规则自动写入通用基线，也不得覆盖其他版本的同名页面标注。
- `public/annotations/` 只在明确维护旧兼容页或已确认的同归属基线时同步；不能因为当前版本变更就机械覆盖公共数据。
- 一批关联的 PRD、原型和标注修改共同完成后，再判断是否形成研发修改记录，不为标注同步单独制造重复批次。
- 按钮触发同步时遵循 [版本标注同步契约](references/version-sync.md)：只读取上次成功同步以来的局部差异，只输出和写入确实需要变化的 `update / add / merge / delete`，不得为了证明“保持不变”而全量检查无关标注。
- 产品在 `/manage/versions` 点击“同步标注”即授权本次局部同步，不再二次确认；如果 PRD / 规则与原型存在真实目标口径冲突，则整批不写入，并明确展示两边口径和具体冲突点。

## 默认执行方式

默认由当前智能体顺序完成需求分析和代码定位，减少上下文与额度消耗。

项目已经登记以下专用角色时，可在用户批准多智能体或任务确实复杂时使用：

- `annotation-prd-analyzer`：只读取证据，输出业务标注候选，不碰代码。
- `annotation-code-locator`：读取候选和页面代码，输出稳定定位与 class 注入清单。

无论是否使用专用角色，都必须遵守同一输出契约和验收规则，不能把“每个字段一个标注”当作完整性。

## 工作流

### 步骤 0：确定页面范围

确认项目根目录、目标路由、pageKey、归属、研发版本、标注 JSON 文件名和页面入口。

- 当版本数据和工作台隔离尚未实现时，`public/annotations/{pageKey}.json` 只服务于旧兼容页或 `pending` 上下文；不得把一个已明确版本的不同规则覆盖写入旧公共 JSON。
- 当 `public/review-data/` 版本清单已启用时，必须按 `versionId/pageKey` 读写标注，并确认 pageKey 已纳入当前版本。

沿真实交互检查同一路由内的页面状态：

- 列表、详情、页签；
- 新增、编辑、发布等抽屉；
- 确认弹窗、详情弹窗、自定义全屏浮层；
- 打开后仍保留底层 DOM 的二级页面。

一个独立路由使用一个 JSON；同一路由中的不同页面状态使用不同 `group`，分别从 1 编号。独立路由才生成独立 JSON。

### 步骤 1：检查运行环境

1. 读取 `package.json`，Vue 使用 `templates/vue/`，React 使用 `templates/react/`。
2. 比较 `.agents/skills/annotation/version.json` 与项目 `src/components/Annotation/version.json`。
3. 项目版本落后时，提醒用户组件模板将被更新，然后同步对应框架的全部模板和根目录 `viteAnnotationPlugin.ts`。
4. 确认根布局挂载 `AnnotationOverlay`、`public/annotations/` 存在、依赖齐全、Vite 插件已注册。
5. 加载路径使用 `BASE_URL + annotations/{fileName}.json`；本地保存使用 `POST /__annotation_save__`。

控制入口要求：

- 工作台顶部只保留“原型标注”入口，控制标注点显示和隐藏并展示总数。
- 本地开发环境在旁边显示“标注编辑”，开启后允许新增、移动、修改和删除。
- 正式构建隐藏编辑入口，但仍可查看标注。
- 不生成底部图钉入口，不使用快捷键进入编辑模式。
- 研发查看面板只展示标题、分类和业务内容，不展示 `source` 来源路径；`source` 仍保留在 JSON 和标注编辑器中，作为产品与 AI 的内部证据。

使用模板导出的 `useAnnotationControl` 接入顶部按钮。若项目没有工作台顶部工具栏，选择现有全局工具栏放置这两个显性入口，不另造悬浮入口。

### 步骤 2：生成业务标注候选

先按页面状态建立 `group`，再决定每组标什么。

合并原则：

- 同一业务对象的字段、状态、计算、操作和结果有强上下游关系时，合并成一个区域标注。
- 列表的展示字段、状态操作和发布限制可以用一个表格型标注说明，不给每列、每个按钮分别打点。
- 同一表单中的输入、校验、提交结果按业务阶段归组，不按控件数量拆分。
- 二次确认文案通常合并到触发操作；确认弹窗存在独立且重要的不可逆规则时，才单独标注。
- 空状态、分页和普通成功提示合并到所属区域，不单独占点。
- 页面名称、底部导航、普通编号复制、显而易见的字段和值等仅复述界面的内容，默认不标；只有存在不直观的权限、状态、计算或下游影响时才保留。

数量原则：

- 不设置固定数量或硬上限，根据业务主题是否独立、标注点空间距离和单条内容长度综合判断。
- 两个标注位置接近且描述同一条业务链路时优先合并；如果合并后内容过长、主题不独立或研发需要反复跳读，则应拆开。
- 页面简单时自然减少，业务层级复杂时可以增加；页面状态越多，可以使用更多 `group`，避免不同状态同时展示。
- 不为追求“少”而遗漏研发必须知道的规则，也不为追求“全”而把每个字段和按钮拆成独立标注。
- 每个可见状态通常优先收敛为少量关键标注；`3～6` 个可作为扫读检查的参考区间，但不是硬上限，最终以业务主题独立性和页面空间为准。

每个候选至少包含：

```text
title / category / content / source / location / container / group
```

### 步骤 3：组织可读内容

标注面向研发扫读，不把 PRD 压缩成一整段。先写结论，再选择适合内容关系的 Markdown 结构：

| 内容关系 | 表达方式 |
|---|---|
| 有先后顺序的操作、校验、流转 | 有序列表 |
| 并列字段、条件、结果 | 无序列表 |
| 状态—条件—操作—结果映射 | 表格 |
| 金额、数量、运量计算 | 单独公式或代码样式 |
| 异常、不可逆限制 | “注意”或“特殊情况”独立小段 |

一个标注最多拆成 3 个主题区块；每个区块只表达一个主题。短字段说明保持一两句话，不为了形式强行使用表格。

- 标题直接写业务对象和规则主题，避免“字段说明”“规则说明”“其他说明”等空泛命名。
- 一段文字超过两个完整规则句时，优先改为小标题和列表。
- “必填 / 选填 / 只读”“修改前 / 修改后”“不同状态的操作结果”等差异必须分组或使用表格，不串成一个长句。
- 展示范围、展示内容、操作条件和处理结果同时出现时，按研发实现顺序分块，不混在同一段。
- 合并后形成超长内容时应重新拆分；精简的目标是减少跳读和重复，不是追求最少数量。

不要使用“快照”等含义模糊的内部词。文案应直接说明业务对象、触发条件、处理结果和异常边界。

### 步骤 4：定位并注入

每个正式标注注入唯一 class：

```text
annot-{pageKey}-{category}-{slug}
```

定位要求：

- selector 固定为 `.{className}`，不使用 UI 库 class、`nth-child` 或猜测选择器。
- class 注入到与标注内容一致的常驻业务区域；条件显示元素应定位到当前状态下稳定存在的祖先容器。
- 默认只追加 class，不改属性、结构和业务逻辑；确实没有稳定宿主时才增加无样式 wrapper。
- 一个 selector 在目标页面源码中应只有一个稳定命中。
- 正式标注初次生成时 `position` 使用 `{ "x": 0, "y": 0 }`；用户在编辑模式拖动后，`position` 保存相对宿主默认锚点的偏移量，`type` 仍为 `selector`，不得清空 `selector` 或转成固定屏幕坐标。
- 修改、合并或同步已有标注时保留用户已经调整的相对偏移量；只有宿主定位发生变化、原偏移已经失效或用户明确要求重置位置时，才恢复为 `{ "x": 0, "y": 0 }`。

容器要求：

| 页面状态 | `container` | 接入方式 |
|---|---|---|
| 普通页面、列表、详情、页签 | `page` 或省略 | 页面内稳定 `.annot-*` class |
| 弹窗、全屏详情浮层 | `modal` | 浮层根节点加 `data-annotation-container="modal"`，内容节点加 `data-annotation-content="modal"` |
| 抽屉 | `drawer` | 使用框架抽屉容器；自定义抽屉采用对应 `data-annotation-*` 显式接入 |

打开浮层后，底层 page 标注必须隐藏；浮层自己的 `group` 从 1 编号。关闭后恢复底层标注。

### 步骤 5：写入 JSON

每条标注使用以下结构：

```json
{
  "id": "annot-order-list-rule-actions",
  "type": "selector",
  "selector": ".annot-order-list-rule-actions",
  "position": { "x": 0, "y": 0 },
  "title": "状态与操作规则",
  "content": "**状态与操作**\n\n| 状态 | 操作 |\n|---|---|\n| 待执行 | 编辑、发布 |",
  "category": "rule",
  "source": "相关 PRD 章节",
  "container": "page",
  "group": "list",
  "createdAt": "YYYY-MM-DD"
}
```

同一 `group` 中的数组顺序就是阅读编号顺序。按照用户实际操作路径排列：入口和基础信息在前，操作过程居中，提交或结果在后。

### 步骤 6：验证

依次执行一次确定性检查：

1. JSON 能解析，字段完整，所有正式标注均为 selector 类型；`position` 必须是有效数值，非零值视为用户相对宿主调整后的合法偏移。
2. 每个 `.annot-*` selector 在目标源码中有且只有一个注入位置。
3. `group` 覆盖所有实际页面状态，组内顺序符合用户操作路径。
4. 检查当前状态的标注密度：既不能密集遮挡，也不能因为过度合并而形成难读的超长标注。
5. 打开抽屉、弹窗或自定义浮层后，底层标注不穿透，当前容器从 1 编号。
6. 长内容能正确渲染标题、列表、表格和公式，且不超过 3 个主题区块。
7. 执行一次全页精简审查：检查重复主题、只复述界面的低价值标注、长段落和相邻可合并项，并记录保持 / 修改 / 新增 / 合并 / 删除的判断。
8. 原型代码改动运行一次项目构建。
9. 用户要求查看效果时，再进行一轮局部浏览器验证；至少覆盖主页面和一个最深子状态。

交付时说明：总标注数、各组和各状态实际可见数量、数量判断依据、修改文件、构建结果，以及发现但未擅自修复的 PRD/页面差异。

## 组件版本

Vue 和 React 模板共用 `.agents/skills/annotation/version.json`。

改动任何模板组件、样式或保存插件后必须把版本号加 1；否则已安装项目无法识别组件升级。

## 禁止事项

- 不跨项目读取 PRD、业务规则或 AgentPM 知识库。
- 不按字段、表格列、按钮数量机械生成标注。
- 不把隐藏元素、重复列表项或不稳定选择器作为正式锚点。
- 不让 page、modal、drawer 的标注同时混在一个可见状态。
- 不自动修改 PRD、业务规则或页面业务逻辑。
- 不为了完整性增加无业务价值的解释和标注点。
- 不把标注文案精简、定位修复、编号修复、来源隐藏等工具层优化写成研发业务变更。

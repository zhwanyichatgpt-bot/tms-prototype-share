# TMS 原型验证

## 产品与目录上下文

首次进入本项目新主题或写入阶段，先读取 `context/project-rules/产品架构与目录治理规范.md`，锁定 productId 或 operationAppId、使用端、scope/projectId 和版本。下文的 prd/、discussions/、prototype/ 等均为资产根目录，实际落点必须展开产品/端与项目层级；不得继续向历史平铺目录写入。共用端不复制进各产品；同主题续接不重复读取。


## 目标

用 Vue 3、Element Plus 或 Vant 生成可点击、可演示、可评审的 TMS 原型，并保证业务页面只作为中央画布内容，不重复创建工作台外壳。

## 上下文前置门

读写原型前必须明确：

```text
需求归属：common / project
所属项目：null / projectId
研发版本：pending / versionId
当前交付：pending / 首次交付 / 第N次变更（内部可映射 R0/Rn）
版本状态：进行中 / 已完成
允许修改范围：页面、状态和交互
```

- 归属不明确时停止写入，只问通用还是定制；定制必须继续明确项目。
- “生成研发地址”每个版本只能执行一次，后续变更始终沿用同一地址。
- “生成研发地址”与“标记完成”相互独立；标记完成不代表业务上线，也不冻结版本。
- 生成地址只写入首次交付数据，不等于 GitHub 已推送或 Netlify 已部署成功。
- 首次交付之后，对研发有影响的页面改动必须自动生成变更记录；不得要求产品负责人再到管理页面重复填写。

## 项目真相源

- 原型根目录：`prototype/`。
- 联运通用门户：`prototype/common/products/lianyun/web/portal/`。
- 联运通用业务 Web：`prototype/common/products/lianyun/web/business/`。
- 通用业务移动端：`prototype/common/products/{productId}/mobile/`。
- 通用司机移动端：`prototype/common/operation-apps/driver/mobile/`。
- 定制项目：`prototype/projects/{projectId}/`。
- 页面注册表：`src/page-registry.js`。
- 路由：`src/router.js`。
- 唯一原型验证工作台：`src/App.vue`。
- 开发：`npm run dev`，构建：`npm run build`，默认端口 `5173`。

开始原型验证时，先按上下文前置门判断 `common / project`，再确定源码落点：

- 通用页面按门户、业务 Web、业务移动端、司机移动端进入对应 `prototype/common/` 子目录。
- 定制项目无差异时直接引用通用页面，不复制源码。
- 项目新增或覆盖页面放入 `prototype/projects/{projectId}/`，并登记来源通用页面或版本和差异用途；不得为了项目需求直接修改通用源码。
- 项目之间不得直接引用源码。可复用能力先单独评估是否进入通用基线，再由各项目选择升级。
- 页面新建、移动或复制后，同时更新 `src/page-registry.js` 和 `review/page-catalog.mjs`；目录级 `sourcePaths` 不得覆盖另一页面的子目录。
- 在其他仓库开始 TMS 原型验证时，先读取当地项目规则；没有更明确规则时沿用以上归属判断和逻辑目录，不得默认写成通用原型。

## 自动记录版本变更

版本数据内部使用修订编号保证递增，但面向用户只表达为“首次交付、第1次变更、第2次变更”，不展示 `R0/R1`。

- 尚未生成研发地址：正常修改原型，不创建变更记录；生成地址时自动形成“首次交付”。
- 已生成研发地址：完成用户确认的修改并通过验证后，必须在这次修改对外部署前自动记录变更，但不再生成地址。
- 已完成版本仍可继续修改和记录变更；完成标记不改变变更记录规则。
- 一组连续讨论并一次完成的相关修改只生成一批变更记录，避免把同一需求拆成多条机械记录。
- 只记录实际完成并验证通过的变化，不记录讨论想法、失败尝试或未落地方案。

自动记录时，根据已确认讨论和实际代码差异整理：修改原因、修改类型、影响页面、修改前、修改后、研发注意事项；页面范围或计划上线日期同时变化时放入 `patch`。然后在项目根目录运行：

```bash
npm run record:change -- --version={versionId}
```

通过标准输入传入 JSON：

```json
{
  "reason": "本次修改原因",
  "patch": {},
  "items": [
    {
      "type": "rule",
      "pageKeys": ["pageKey"],
      "before": "修改前",
      "after": "修改后",
      "devImpact": "研发注意事项"
    }
  ]
}
```

命令成功后才能在交付中说明“变更记录已生成”。命令失败时保留已完成的代码修改，明确报告记录失败原因，不伪造成功状态，也不改为让产品负责人手动补填。

## 指定版本发布

- 修改原型和记录变更是本地任务；GitHub 推送和 Netlify 部署是外部动作，必须另有用户对具体版本的明确发布确认。
- 用户只说“全部上线”或“发布”而存在多个版本时，先列出版本名称和 ID，不直接推送。
- 发布前确认目标版本、页面清单、标注与版本数据、变更记录、必要的共享依赖以及明确排除的无关改动。
- 修改共享原型页面时，查看页面注册和版本索引，列出其他引用它的版本；不得默认只影响当前版本。
- 本地脏工作区构建通过后，还要验证精确暂存快照的依赖闭包和构建结果；不得让未暂存文件掩盖远程缺失依赖。
- 推送后等待 Netlify 结果，再验证固定研发地址、版本数据、变更数据和标注数据可访问；只有完成这些检查才能声明发布成功。
- 管理页部署状态回显、单按钮自动提交发布、精确文件自动归属和真正不可变的版本快照尚未实现，不得将它们当作已有能力承诺。

## 执行模式

### 同主题续接

- 不重读 Skill、PRD、设计规范或整页代码。
- 需要改文件时只读目标片段，一次补丁、一次 `npm run build`；已首次交付的版本按上节自动记录变更。
- 不调用子智能体、reviewer、浏览器或 dev server。

### 单页局部修改

1. 读取目标组件、注册表必要条目、当前上下文直接规则和已有设计记录。
2. 列出实际受影响文件，不触碰与任务无关的页面。
3. 一次实现、一次构建、最多一次确定性局部修复。
4. 只在用户要求看效果或报告具体视觉/交互问题时启动局部浏览器检查。

### 新页面或完整重设计

1. 按“当前版本 → 当前项目 → 通用基线”读取必要 PRD 章节、业务规则、工作台入口和设计规范。
2. Web 端使用 Vue 3 + Element Plus，移动端/H5 使用 Vue 3 + Vant 4。
3. 根据 `common / project`、端别和模块层级选择上述物理目录实现页面，同时在 `src/page-registry.js` 和 `review/page-catalog.mjs` 登记；定制覆盖页必须保留来源通用页面或版本和差异用途。
4. 复用唯一原型验评工作台，禁止在画布内再生成顶部工具栏、原型目录、“返回原型目录”或模拟的第二层业务工作台。
5. 高消耗的多页批量、仓库级探测、独立 reviewer 或多智能体必须先获得确认。

## 实现边界

- 只做验证原型，不接真实后端。
- 页面要像真实业务系统，不把规则说明、待确认卡或研发文档放入页面主体。
- 缺失规则标记待确认，不擅自定案。
- 不擅自修改 PRD、讨论记录或业务规则。
- 不复制原型工作台控件，不为单页创建独立返回入口。

## 验证与交付

- 只改文案或说明：做目标内容自查。
- 原型运行时代码改动：运行一次 `npm run build`。
- 用户明确要求视觉检查：最多一轮局部浏览器验证。
- 交付时报告改动文件、构建结果、所属范围、版本变化和已知问题；已首次交付版本同时报告自动变更记录结果。
- 只提示用户验证原型或选择下一步，未经用户认可不自动反哺 PRD。

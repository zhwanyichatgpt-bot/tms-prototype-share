## 结算功能（按运单逐单结算）

**画板来源**：超好飞设计稿（Pixso 文件「超好飞」）`11:104` 运单（结算）、`13:13` 单笔金额调整、`6:9583/6:3388` 结算单管理、`6:3690/6:3832/6:3966/6:4120` 结算单详情。基准 750×1624 @2x → 验收视口 375×812。**只借用视觉与交互形态，结算粒度已按智运的资金结构重新定，见下。**

**业务口径**（2026-09-26 讨论确认，已沉淀至同日货主端结算粒度讨论记录）
- **按运单逐单结算**，不做批量结算、不做结算单对象。竞品依据：高德作为聚合层不参与旗下平台与司机的结算；运满满以「确认收货」这个运单级业务事件触发自动分账，平台不做人工二次核算。
- **资金结构**：货主付款 → 承接平台（自动扣佣）→ 司机。货主付的是**运费全额**，平台抽佣在平台侧自动完成，货主端不展示抽佣，也不做附加服务费（后续如需再加）。
- **状态三态**：`待结算 → 待付款 → 已结算`。没有「处理中」——那是平台侧核验，不进货物端。
- **装卸货凭证齐全才能结算**，这是硬约束，不齐只给「补凭证」。设计稿里的「核算凭证」（必传附件）**不做**：没有必要，运单自带的装卸货凭证已经是核算依据。
- **不做驳回**。设计稿里的「驳回」文案挂在名为「作废（次要按钮）」的图层下，是改文案残留，不是独立设计。
- 钱包不在本次范围，由「我的」模块单独做完整钱包体系；付款方式当前为占位。

**组件树**：`App.vue` → `WaybillPage.vue`（结算模式）/ `WaybillSettlePage.vue`（单运单结算页）。

**数据**：结算字段直接挂在 `mock-data.js` 的 `waybillList` 上（单一数据源，运单的结算就是运单自己的状态）：`unitPrice` 单价、`settleType` 结算态、`settleNo/settleTime/paidTime` 结算与付款信息、`adjustAmount` 金额调整、`settleRemark` 结算说明、`vouchers.load/unload` 装卸货凭证。`platformEntities` 提供承接平台结算主体全称。

**字段映射**：超好飞的 运输机型→车型、吊运重量→计费吨位、服务商→承接平台、飞手→司机、货源计划→货源。

**页面结构**
- **结算列表**（运单页结算模式）：页签「全部 / 待结算 / 待付款 / 已结算」；只收已送达的运单（已装货/在途还没卸货，谈不上结算）。卡片：状态 + 运单号 + 应付金额 · 路线 · 货品/计费吨位 · 承接平台 · 卸货时间 · 车型/司机。按钮按状态出：`补凭证`（凭证不齐）/ `去结算` / `付款` / `查看`。
- **单运单结算页**：运单信息 → **计费明细（单价 × 吨位 = 运费小计）** → 金额调整（增加/减少/按比例，核增核减需填原因）→ 装卸货凭证（齐全才可结算，缺则可补传）→ 结算说明 → 底部「确认结算」。确认后转「待付款」，底部变「确认付款」并显示收款方（平台结算主体全称）。
- `WaybillPage` 用 `v-show` 挂载以保留结算模式的滚动与页签状态；结算页隐藏底部 Tab 栏。

**验收**：`npm run build` 通过。浏览器（375×812）实跑：结算列表 → 去结算 → 计费明细核对 → 核减 38 元并填原因 → 确认结算（3,038 → 应付 3,000）→ 确认付款 → 列表状态更新为「已结算」且停留在结算模式。7 条运单的「单价 × 吨位 = 运费」全部核对一致。

**待确认**
- 付款方式的真实形态（钱包余额 / 银行直连）待钱包模块定。
- 已结算运单是否要展示付款流水号/凭证。
- 发票入口仍走「我的 → 我的发票」，与本次结算的衔接未定（先款后票）。
- 单运单结算下货主要给同一平台连付多笔，是否需要「一次操作发起多笔」的便利入口（每笔仍独立交易）。

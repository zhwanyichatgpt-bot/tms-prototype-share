# 至简智运货主端：首页 PRD

## 0. 快速理解

首页服务货主三个任务：快速开始发布货源、了解全部进行中运输及异常、发现司机并进入详情判断。司机推荐发生在填写本次货源之前，不把历史画像描述为本次货源已经匹配成功。

本文件是首页Tab的独立需求基线，承接多次讨论，不是当前页面的逐项抄写。第1—7章为已确认方向与执行边界；影响取数、算法和闭环的未收口部分集中在第8章。本文件处于待评审阶段，不代表本轮变更已对外部署。

核心决策：

- 首页仅保留一个“快速发布”主入口，不拆单车/批量，不保留常用路线快捷行。
- 一张进行中运输卡汇总全部执行中货源，异常优先，单票内容进入二级列表。
- 推荐主体只为个体司机；一个司机一张卡，多辆车在司机能力内表达。
- 首次推荐依据历史发货线路；新用户可随机发现司机；之后使用主动筛选，不和发货表单联动刷新。
- 图片上显示合作次数；卡片保留整体准时率、履约单数、来源标签和推荐百分比，不改原视觉体系。
- AI分析、对话、行情及办理页面不纳入本首页PRD；发布全表单属于后续货源PRD。

## 1. 背景、目标与范围

### 1.1 历史演进与取舍

| 来源 | 本次沿用 | 本次替代或剥离 |
| --- | --- | --- |
| 9月15日首页与AI合并PRD | 单一发布主动作；推荐有承运事实；不用无来源可装时间；保留原设计语言 | 删除常用路线；不再采用单票横向在途卡；AI独立处理 |
| D03，9月20—22日 | 浏览司机在填货前；定向是邀请而非派单；司机自主接单；平台履约与货主合作记录分来源 | 首页不再混排车队/物流企业；图片不用司机头像；不把司机评分加成第三组评级 |
| 9月21日联合评审及9月23日收口 | 进行中运输总览、异常优先；经营与AI分开；已有二级业务复用 | 旧导航中的独立运单Tab不作为当前首页导航事实 |
| 9月29日本次讨论 | 司机维度、多车能力、平台标签、合作图片角标、准时率、百分比；主动筛选、新用户随机 | 不由当前货源条件触发联动推荐；去掉登记车辆数量与额外邀请开关 |

今天的“只展示司机”只替代首页推荐范围；不据此断言所有其他入口的历史车队能力已经取消。

### 1.2 用户与目标

货主查看自身业务范围内的货源执行与合作记录，浏览平台可展示的司机资料。平台提供司机身份、承运履约及定向承接能力；司机决定是否承接，首页不能替司机承诺接单。

目标：减少发布入口查找；让货主一眼区分执行规模与异常待办；用真实承运、车辆能力及合作记录支持选择司机，避免无依据的实时可用性和匹配承诺。

### 1.3 页面边界

| 纳入首页PRD | 只说明衔接、不展开 |
| --- | --- |
| 品牌、定位/地图场景及快捷发布入口 | 定位授权、真实地图服务、地址库维护 |
| 进行中运输汇总与分类下钻 | 货源列表/详情、运单执行、异常核查与申诉制度 |
| 司机来源、首次推荐、筛选与卡片 | 平台接入实现、完整运力管理与跨平台成员维护 |
| 司机详情的信息职责与定向入口 | 发布表单、定向对象确认、发布结果、并发共享货量 |
| 底部Tab之间的入口关系 | 经营、我的、账户、付款与开票全量规则 |

当前导航为首页、货源、小简AI、经营、我的。保留这一导航关系作为页面上下文，不修改导航；AI内容本次剥离，现有“小简洞察”区域和跳转只作为历史实现说明，不据此新增AI需求或授权删除页面。

## 2. 角色视角流程

### 2.1 发货

1. 货主进入首页，可选择装货、卸货地址，也可直接点击快速发布后补充。
2. 系统进入同一个货源发布流程，不因地址未填而改为另一个发货入口。
3. 已选择的地址应供发布流程核对；未选择的不以历史或地图示例冒充本次确认。当前原型尚未完成首页到发布页的地址传递，见第8章。
4. 发布流程负责补充信息、选择平台/方式、确认及返回业务结果，首页点击入口本身不创建已发布货源。

### 2.2 查看进行中运输

1. 货主查看汇总卡：执行中货源数、涉及车辆数、异常待关注、今日待装货、今日预计送达。
2. 点击查看全部/总览进入二级货源列表；点击分类数字应带入对应分类；点击异常提示进入异常关注范围。
3. 从列表查看单票货源及关联运单；后续核查、反馈或处理在相应业务页办理。
4. 首页不直接把异常标为已解决，不以车辆恢复行驶推定货品安全。

### 2.3 浏览司机与定向发布

1. 系统生成初始列表：有历史以历史线路找候选司机；全新用户随机发现司机。老用户历史不足的归类见第8章。
2. 货主按线路、车型主动筛选；修改快速发布信息不改变该列表。
3. 点击司机卡进入司机详情，查看运输能力与履约合作事实。
4. 在详情发起定向发布，携带司机身份和来源平台进入同一发布流程。
5. 发布模块确认定向范围后，被指定司机看到货源并自主承接；首页不派车，也不因选司机生成已接单任务。

## 3. 核心对象与状态

### 3.1 对象及关系

| 对象 | 含义 | 关系和边界 |
| --- | --- | --- |
| 货源计划 | 货主一次组织运输的对象，可由多车执行 | 汇总以货源计票，不把一辆车或一张运单算一票货源 |
| 运单/司机接单任务 | 货源下的具体执行 | 接单不等于装货或完成；与计划共享剩余量的规则由货源模块维护 |
| 装卸地址 | 本次意向装卸地点 | 首页选择不是确认发布；不自动复制历史货品、价格、日期 |
| 历史线路 | 由已发生业务记录形成的方向城市对 | 发货方历史用于推荐上下文，司机历史用于承运能力，不能互相替代 |
| 推荐司机 | 接入平台提供的个体司机 | 一个司机可关联多车、多条历史线路；来源平台不是推荐物流公司主体 |
| 车辆能力 | 司机关联车辆的车型与载重 | 展示能力而非保证实际出车；实际车辆由承接执行时确定 |
| 合作记录 | 当前货主与司机的已发生运输合作 | 聚合方关联记录，与来源平台整体履约不同 |
| 异常事件 | 货源/运单下的风险及处理事件 | 疑似风险、平台确认结果和处理进展分别记录 |

### 3.2 页面状态与允许操作

| 状态或条件 | 允许操作 | 结果与禁止事项 |
| --- | --- | --- |
| 首次进入、地址未填 | 选址或进入快速发布 | 不自动把历史线路当本次装卸地址 |
| 地址已选 | 修改地址、进入发布流程 | 推荐列表不随之自动重算 |
| 有执行中货源 | 查看总览及分类 | 不在首页逐票铺开 |
| 存在异常 | 查看异常对应业务范围 | 货主从首页不能直接确认安全或结案 |
| 有可用历史 | 浏览相关司机、主动筛选 | 不标“适合这票货”，因为尚未确认本次货源 |
| 全新用户无历史 | 随机浏览、主动筛选 | 不伪造常发线路或合作次数 |
| 筛选后无司机 | 调整或清除筛选 | 不用不符合条件的司机静默填满结果 |
| 司机详情发起定向 | 进入填写及确认发布 | 司机未自主承接前不得标为已接单 |

### 3.3 多对象变化

点击首页发布入口只产生填写上下文；确认发布由货源模块产生发布结果。司机承接才形成任务及相应货量占用，装货处理差额；这些事件的共享量与并发细节由货源PRD管理，不在首页另建规则。首页汇总根据业务状态更新，不由AI推测修改状态。

## 4. 核心业务规则

### R01：发布入口唯一，删除常用路线快捷行

保留“快速发布”，不拆分单车/批量，不增加并列查找运力主按钮。不展示常用路线两个标签和设置入口，不因删除快捷行取消手动选择装卸地址。来源：早期PRD R01及9月29日用户确认。

### R02：首次推荐与发布表单分离

推荐在填货前生成。有历史按货主历史线路与司机历史承运记录建立关联；新用户随机展示。货主选择本次装卸地址、货品和价格不触发联动刷新。之后仅由推荐区域主动筛选改变条件。历史线路取数、阈值和候选池细则见第8章，不由固定示例线路替代。来源：D03背景、9月29日确认。

### R03：只推荐司机，车辆作为司机能力

首页不混排物流公司或车队。一个司机一张卡，可展示其多辆车的车型、载重，不把车拆成多张司机卡，也不展示“登记车辆数”作为主体指标。不增加“允许接收定向邀请”开关。司机级运力可展示、定向可见与接单资格校验按平台支持作为设计前提。来源：9月29日确认。

### R04：执行汇总以货源为粒度，异常优先

一张卡覆盖货主全部执行中货源，不用横向逐票计划卡。货源数、车辆数分别统计；异常、今日待装、今日预计送达是分类观察，不能直接相加当总量。提示显示具体关联事件，不虚构异常；“预计送达”不是保证送达。来源：唯一进度表D05/T05及9月23日变更。

### R05：合作、履约和推荐百分比分开

合作次数回答“当前货主与该司机合作了多少次”，放车辆图片角标；平台整体履约单数与准时率回答“司机整体跑得怎样”；推荐百分比回答“推荐关联程度”，不是服务评分、履约成功概率或准时率。不再增加卡片司机服务评分。准时率不用单条线路的小样本口径。来源：D03 4.4/4.5及9月29日确认。

### R06：历史线路必须可追溯，不当成实时状态

线路带方向与承运趟数，统计对象为司机实际承运经历，不按名下某一车辆代替司机。司机有多条线路时，卡片展示和详情展开要区分；具体代表线路取舍见第8章。不能用车型、路线推断货品经历，也不展示无来源“明日可装”、当前空闲、距装货点最近。来源：早期PRD R07、D03 4.4、9月29日讨论。

### R07：定向是邀请，不是派单或货量预分配

详情先于填写本次货源；发起定向仅带入司机身份，仍须核对货源及发布范围。司机在所属平台自主接单，不由货主挑选其名下车辆后直接派车。已有D03多对象邀请与不预分配货量方向仍作为下游历史依据，首页本期不擅自增加多选管理界面。来源：D03 2.1及本次司机、多车讨论。

### R08：页面延续既有UI，业务不等待AI

保留原有卡片、图片区、紧凑字段、标签与弹层语言。合作次数放图片，来源平台做标签，推荐值保留百分比。AI不作为发布、查看执行或选择司机的前置步骤；本PRD不规定AI分析规则。来源：早期R09及用户本次对过度改版的纠正。

## 5. 功能详细说明

### 5.1 顶部与发货入口

保留品牌与地图场景，发货区域明确装货、卸货两端，点击分别选择地址；点击快速发布进入货源流程。首次进入不把常用地点、定位地点或地图示例视为已确认装货地。顶部定位和地图只是场景信息，不等于本次发货地址。

首页只呈现快捷入口，不把平台选择、完整货品表单、核算模板、路耗或发票申请塞进首页。已选择的地址到发布页仍可更换；字段必填、日期选择等见本次讨论记录，后续由货源PRD统一维护。

### 5.2 进行中运输卡

卡片内容顺序为总量与车辆规模、分类数字、优先异常提示。查看全部进入全部执行范围，分类分别进入异常待关注、今日待装货、今日预计送达范围。只呈现有业务数据支持的结果；无异常不显示有事件语气的异常提示。

异常详情可定位到关联货源/运单，后续由平台核查并回传处理。早期已确认异常方向为轨迹偏离和货品安全；当前原型仍出现“预计延误3小时”示例，不能据此替换已确认异常范围或承诺预测能力。

### 5.3 司机推荐与筛选

推荐来源为第三方平台的司机级运力，而不是从货主运单凭空生成司机或把平台物流公司当司机。货主历史线路与平台司机承运城市对建立候选关系；全新用户采用随机发现。来源平台提供司机履约事实，聚合方关联本货主合作记录。

筛选保留“综合推荐（新用户随机展示）/线路/车型”的信息分工。线路和车型由货主主动选择；清除筛选回到初始推荐上下文。多车司机只要存在满足所选车型的车辆能力，即可作为候选，卡片不能把其他车辆暗示为筛选命中车辆。当前原型已做到筛选车型优先展示，这是实现事实，不替代代表照片和排序尾项确认。

空结果明确显示“暂无符合条件的司机，请调整筛选条件”。新用户不得显示“根据你常发某线路”；可以显示该司机实际跑过的线路。随机分配不等于每次点击必须换一批，刷新频率见第8章。

### 5.4 推荐卡片

| 位置 | 内容 | 口径 |
| --- | --- | --- |
| 左侧图片 | 车辆图片 | 不用司机头像；无图与多车代表图规则见第8章 |
| 图片角标 | 合作过N次 | 本货主与该司机的合作，不是平台全体履约 |
| 右侧首行 | 司机名称、N%推荐 | 名称对应司机；百分比不与准时率混同 |
| 车辆行 | 车型与载重、多车能力 | 不展示登记车辆数，不承诺哪辆车将实际执行 |
| 线路行 | 历史方向线路及趟数 | 有可追溯承运事实；多线路详情可展开 |
| 底部标签 | 履约N单、准时率N%、来源平台名称 | 平台整体司机履约；来源标签不用公司规模替代 |

早期“常运货品”仍是司机能力信息，可在详情承载；本次紧凑卡片不强制再加货品行。车牌不是首页推荐核心；不添加认证、好评率等未经本次列表收口的额外标签。

### 5.5 司机详情及发布衔接

点击卡片进入对应司机详情，身份、车辆、历史线路、履约及合作数据应与列表一致。沿用D03的信息职责：说明是谁、能运什么、跑得怎样、与本货主的合作情况，不套用物流公司车队规模。

详情可展示多条历史线路与多车能力；主动作指向定向发布。若司机尚无本货主合作，只能说明没有合作记录，不能伪造次数。平台不具备某指标时不能用精确示例顶替真实数据。

定向发布需保存司机标识与来源，进入货源填写、发布范围确认及成功反馈；这一入口不要求货主先填写完整货源才能浏览司机。当前原型只有首步身份横幅，未完成最终对象确认与司机端承接闭环，详见第8章。

## 6. 上下游联动

| 模块 | 首页提供/接收 | 业务边界 |
| --- | --- | --- |
| 货源发布 | 普通发布的已选地址；定向发布的司机身份与来源 | 单一流程，发布模块负责最终确认；首页不生成已发布结果 |
| 货源列表/详情 | 全部执行、异常、待装、预计送达的分类上下文 | 二级按一票货源呈现，关联运单进一步下钻 |
| 司机详情/平台运力 | 司机身份、车辆、承运与履约事实 | 平台数据可展示是假设能力前提，真实接入单独实施 |
| 司机端/接入平台 | 已确认货源与定向可见范围 | 自主承接；取消额外邀请开关不取消可见与接单资格处理 |
| 我的/运单结算 | 仅保持业务入口关系 | 延续9月26日逐运单结算；首页不重新建结算单或批量付款规则 |
| 经营 | 保持独立Tab | 基础经营数据不藏入AI；本文件不定义经营指标 |

货源接单量、装货差额释放和平台可用性继续沿用既有专题方向，由货源PRD收口具体计算。首页“是否需要开票”的下游衔接不改变历史额度规则，未开票货源是否也受额度限制不得自行推断。

## 7. 字段与枚举

### 7.1 首页业务信息契约

| 字段组 | 信息 | 来源与显示约束 | 操作联动 |

### 7.2 页面状态枚举

推荐上下文分为有历史推荐、全新用户随机发现，老用户历史不足的处理见H02；结果分为有候选、筛选无结果。执行汇总分为有/无执行中货源、存在/不存在异常。这里只定义首页状态，不替代货源、运单或平台发布状态字典。

## 8. 待确认、原型差异与追溯

### 8.1 待确认事项（研发前需收口）

| 编号 | 已确认部分 | 未确定部分与风险 |
| --- | --- | --- |
| H01 | 地址可手选，进入同一发布流程 | 初始空值与历史常用地点的关系、地址传递及定位入口；原型首页仍有默认地址但发布页为空，避免用户选择丢失 |
| H02 | 老用户历史线路推荐、新用户随机 | 何谓可用历史、取发货计划还是已完成运单、周期、次数、同次数排序、多装卸点归并；没有历史的老用户如何归类 |
| H03 | 司机级来源、无额外邀请开关 | 可展示候选池的认证/有效性条件、平台标识、跨平台同司机去重；不擅自加“可承接状态/服务区域”模糊门槛 |
| H04 | 主动线路/车型筛选，不联动发货表单 | 候选池范围、排序、列表条数、分页与随机刷新；原型显示最多5位及按日固定随机，未正式确认 |
| H05 | 司机历史线路带趟数 | 近180天、同向至少3趟仅为讨论参数，需确认；多条常跑线路如何选代表与并列排序、无足够样本如何表达 |
| H06 | 保留推荐百分比，与准时率分开 | 原型使用60/20/20示例权重，但排序先合作再线路，与分值可能矛盾；公式、排序一致性、新用户是否显示百分比需收口 |
| H07 | 准时率用整体口径，合作是当前货主维度 | 完成状态、撤销/异常单纳入、履约周期、提货/到货误点、司机责任、无样本处理、数据更新与跨平台统计 |
| H08 | 车辆图片、司机可关联多车 | 代表车辆照片、无图兜底、同车型多车排序、隐藏登记车辆数量但展示更多车型的展开方式 |
| H09 | 一张卡汇总全部执行中货源 | 执行状态清单、同车多运单去重、跨日/时区、异常计票、预计送达来源、优先事件排序、零状态呈现 |
| H10 | 分类点击应带条件进入货源列表 | 原型点击只切到列表且未确认分类真正生效；返回首页的筛选和滚动恢复方式 |
| H11 | 定向是邀请，自主接单 | 发布第二步保留对象、来源平台对应关系、成功范围、司机端可见与资格校验、失效/取消及并发承接；入口实现不等于闭环完成 |

这些是已暴露的实现与验收缺口，不是新增业务能力。未收口前不能将示例权重、固定城市、5位司机或98%准时率作为正式验收常量。

### 8.2 原型与需求的明确差异

首页默认地址、静态进行中汇总、延误预测示例、推荐固定线路及示例排序均只证明当前展示状态，不证明上述口径已实现。新用户预览仅切换推荐区域，不等于整页新用户场景完成。首页AI洞察仍在页面，但本文件不承接其内部规则。今天发布表单改动已另存讨论记录，后续货源PRD统一维护。

本次只做文档整理，不自动修改这些原型差异，不写标注，也不发布。当前版本标注中与首页常用路线、汇总层级、推荐司机字段有关的内容在发布前需局部同步；发布表单标注由货源范围处理。

# Pixso设计稿还原与原型源码治理规范

本文用于所有依据 Pixso 设计稿生成或修改 TMS 原型页面的任务。新工具、新对话和后续项目进入此类任务时，必须先读取本文，再读取目标页面、设计稿和项目归属资料。

本文解决四个问题：

1. 尽量保持设计稿视觉一比一；
2. 不把 Pixso 原始导出的上万行节点代码直接变成长期源码；
3. 让多个页面复用 TMS 系统框架和稳定业务组件；
4. 减少反复全页读取、覆盖式脚本和多轮目测返工。

## 1. 核心原则

### 1.1 视觉一比一，不等于源码一比一

- Pixso 是视觉、结构和素材证据源，不是最终 Vue DOM 的唯一组织方式。
- 最终页面必须在指定视口下与设计稿保持视觉一致，但源码应使用语义化组件、数据循环和清晰样式。
- Pixso 输出的 HTML、节点树和 CSS 只能作为生成输入或校对依据，不得未经治理直接成为长期运行页面。
- 不得使用 `26_148` 一类设计节点编号承担业务逻辑、事件控制、组件通信或长期测试定位。

### 1.2 原型验证工作台与TMS业务系统框架分离

- `src/App.vue` 中的顶部工具栏、页面目录、中央画布和标注能力属于唯一原型验证工作台。
- Pixso设计稿中的TMS系统顶部栏、工作台页签栏、左侧导航属于业务系统自身框架，是被验证页面的一部分，必须保留。
- 禁止在业务页面中复制原型验证工作台；也禁止以“只能有一个工作台”为由删除TMS业务系统框架。
- TMS业务Web页面共同使用的系统框架必须提炼到 `prototype/common/shared/web/`，不得在每个页面复制一份。

### 1.3 先证据、后结构、再开发

禁止“先生成整页代码，再凭截图不断打补丁”。固定顺序为：

1. 锁定需求归属和页面范围；
2. 锁定Pixso画板、目标视口和页面状态；
3. 获取视觉、结构、样式和素材证据；
4. 先形成组件与数据结构；
5. 分区实现；
6. 截图差异校验；
7. 清理临时产物并做源码验收。

## 2. 开始任务前必须锁定的上下文

```text
需求归属：common / project
所属项目：null / projectId
研发版本：pending / versionId
当前交付：pending / 首次交付 / 第N次变更
目标页面：页面名称与运行路由
Pixso来源：文件、画板名称、节点ID或容器链接
设计基准：画板宽高
验收视口：至少一个固定宽高
页面状态：默认、展开、抽屉、弹窗、浮层等
允许修改范围：本次页面、公共组件和资源
```

- 需求归属未确认时不得开始写页面。
- 设计画板、验收视口或目标状态不明确时，先读取Pixso和现有页面，不凭经验补全。
- 只有设计稿明确存在的字段、状态、操作和视觉效果才允许实现。

## 3. Pixso设计稿准备标准

设计稿越结构化，MCP读取和代码生成越稳定。进入批量还原前，优先要求设计侧完成：

- 图层使用业务语义命名，避免长期保留“矩形123”“组456”。
- 重复卡片、状态标签、系统顶栏和导航使用组件及实例。
- 状态差异使用组件变体表达。
- 颜色、字体、圆角和常用间距使用设计Token或统一样式。
- 列表、表单和规则排列优先使用自动布局。
- 复杂页面按系统框架、筛选区、主体列表、展开区、弹层和分页分组。
- 图标和图片明确可导出节点，不把多个无关图标合并为一张大图。

若设计稿暂时无法整理，也必须由开发工具在生成代码前建立语义组件映射，不能把混乱图层原样复制进源码。

## 4. Pixso MCP标准读取方法

### 4.1 连接检查

- 保持Pixso客户端、目标文件和目标画布处于打开且激活状态。
- 使用选择模式时只选择一个目标容器；复杂页面先选整页建立基准，再分区选择。
- 先读取页面顶层画板或当前选择，确认文件、画板名称、节点ID和尺寸正确。
- 连接失败时只做连接诊断，不使用旧截图或其他页面冒充当前设计稿。

### 4.2 每个页面必须取得四类证据

1. **视觉证据**：导出完整画板PNG，作为固定基准图。
2. **结构证据**：读取画板和分区的节点层级、名称、坐标及尺寸。
3. **样式证据**：读取字体、颜色、边框、圆角、阴影、间距和布局关系。
4. **素材证据**：图标优先导出SVG；位图按设计尺寸导出PNG/JPG。

只有截图而没有结构数据，会导致大量目测猜测；只有节点代码而没有基准图，会失去最终视觉判断。四类证据缺一不可。

### 4.3 大页面必须分区读取

- 不得一次把包含大量图层、蒙版和重复卡片的整页节点全部送入模型后直接生成最终页面。
- 首次只读取整页的顶层结构和基准截图。
- 再按“系统框架—页签/筛选—主卡片—子行—弹层—分页”逐区读取。
- 重复列表只详细读取一个完整样本及各状态差异，不重复读取五套相同结构。
- 工具返回节点上限或内容被截断时立即缩小区域，不提高上限反复重试。

### 4.4 当前可使用的MCP能力

当前设计连接可用于：

- 获取当前选择及子节点；
- 获取当前页面顶层画板；
- 按节点ID读取分区结构；
- 导出节点PNG/JPG/SVG/PDF；
- 批量下载图标SVG；
- 在插件上下文执行只读脚本，归一化提取文字、坐标、尺寸和样式。

若启用Pixso官方MCP的 `getCode` / `getImage`，其输出仍然只是模型输入：`getCode` 提供的HTML不得直接作为长期Vue源码，`getImage`用于素材和视觉基准。

## 5. 设计组件与代码组件映射

### 5.1 映射优先级

1. 已有TMS公共业务组件；
2. 项目指定组件库（当前Web为Element Plus）；
3. 页面级复合组件；
4. 最后才使用普通HTML元素。

### 5.2 公共组件判断

满足以下条件之一时评估公共组件化：

- 两个及以上页面具有相同业务含义、交互和主要视觉；
- 虽只在一个页面使用，但属于稳定系统框架；
- 结构复杂、状态清晰，并会在列表、详情、抽屉或弹窗复用。

仅视觉相似但业务含义不同的内容，不强行合成“万能组件”；可以共享Token和基础样式。

### 5.3 TMS Web建议分层

```text
prototype/common/shared/web/
├── layout/          # TMS系统顶部、工作台栏、左侧导航、页面容器
├── components/      # 页头、状态页签、筛选栏、分页、空状态等
├── business/        # 企业信息、运输进度、货物摘要、地址节点等
├── styles/          # Token、字体、间距、颜色、层级
└── assets/          # 公共Logo、图标和业务系统框架素材
```

- 门户端、业务移动端、司机移动端分别维护自己的共享层，不直接套用业务Web框架。
- 定制项目无差异时引用通用组件；有差异时使用属性、插槽或项目包装组件，不得把定制规则写入通用组件。

## 6. 页面源码生成标准

### 6.1 页面入口

- `App.vue`只负责公共框架接入、页面组件组合和页面级状态。
- 建议将`App.vue`控制在300至500行以内；不为压缩行数牺牲可读性。
- 单个组件承担一个明确职责，避免巨型组件和大量只有几行的碎片组件。

### 6.2 重复内容

- 设计稿中出现多条列表、任务卡片或子任务时，源码只保留一份结构，通过Mock数据循环渲染。
- 状态、标签、颜色和可用操作使用映射表或计算属性，不复制多套模板。
- Mock数据必须匹配设计稿展示内容，不得为了代码方便擅自改字段或文案。

### 6.3 布局与定位

- 业务布局优先使用Flex、Grid、正常文档流和明确的行列尺寸。
- 绝对定位只用于确实固定的装饰、图标叠加或设计稿明确的浮层，不用于整张业务列表。
- 固定画板还原应定义唯一设计基准尺寸，再由页面级缩放或外层滚动承接。
- 页面内部不得再创建与外层工作台竞争的横向、纵向滚动容器。

### 6.4 样式

- 公共框架样式、公共业务样式和页面专属样式必须分离。
- 页面样式限定在稳定根节点下，不修改全局`body`、`#app`或其他页面。
- 颜色、字号、行高、间距、圆角和层级优先转为Token或CSS变量。
- 禁止通过不断叠加`!important`补丁掩盖错误结构；出现系统性错位时回到布局层修正。

## 7. 固定执行关卡

### 关卡A：设计证据包

开发前必须具备：

- Pixso完整基准图；
- 画板尺寸和验收视口；
- 页面顶层结构；
- 各区域节点数据；
- 图片与图标清单；
- 页面状态清单；
- 复用组件候选。

缺少关键证据时不得直接生成整页。

### 关卡B：结构方案

写代码前先给出：

- 公共组件复用清单；
- 页面组件树；
- Mock数据结构；
- 滚动和缩放方式；
- 拟修改文件。

结构方案不得自行改变设计内容。

### 关卡C：分区实现

- 先实现公共系统框架或复用已有框架。
- 再按筛选区、主体、展开区、弹层和分页实施。
- 一个区域通过局部检查后再进入下一区域。
- 禁止每次失败都重新生成整页或新增覆盖脚本。

### 关卡D：视觉校验

1. 使用与Pixso相同的固定视口生成本地截图；
2. 将本地截图与Pixso原图叠加或生成差异图；
3. 按区域检查位置、尺寸、换行、颜色、字体、边框和素材；
4. 结合DOM尺寸检查滚动、溢出、重叠和居中；
5. 只修改存在差异的区域；
6. 完成一轮局部复检。

字体抗锯齿可能产生少量像素差异，不能只凭全图差异比例判断；必须结合关键元素尺寸和人工视觉检查。

### 关卡E：源码与交付验收

- 重复结构已经数据化；
- 公共框架只有一份实现；
- 无Pixso节点ID业务依赖；
- 无重复导出页面、无无引用组件；
- 无一次性生成脚本、截图、差异图或导出JSON残留；
- 页面注册和`page-catalog`共享依赖完整；
- `npm run build`通过；
- 用户要求视觉验证时完成一轮局部浏览器检查。

视觉通过但源码仍是上万行重复节点，不算完成；源码整洁但视觉未通过，也不算完成。

## 8. 固定视口与响应式边界

- 只有一张1920×1364设计稿时，先保证该基准画板及用户明确的验证视口一致。
- 不能在没有响应式设计规则的情况下承诺所有屏幕尺寸都像素级一比一。
- 若需要1440、1366或移动尺寸，必须提供对应画板或明确断点、缩放、折行和隐藏规则。
- 同一页面多个状态必须分别取得设计依据；不能用默认状态截图推测弹窗、展开行或悬停态。

## 9. 低消耗规则

- 同一任务只建立一次设计证据包，后续修正复用，不重复读取整页节点。
- 完整画板只用于基准图和顶层结构；详细信息按区域读取。
- 重复列表只读取一个完整样本和状态差异。
- 不为同一问题连续生成多个覆盖脚本；一次定位、一次补丁、一次必要复检。
- 临时截图和差异图放在临时目录，任务完成后清理。
- 达到项目工具预算仍无法确认时，报告具体差异和阻塞，不继续扩大扫描。

```text
请先完整读取项目AGENTS.md和：
context/project-rules/Pixso设计稿还原与原型源码治理规范.md

本任务要求依据Pixso设计稿高还原实现，但禁止直接把整页Pixso导出HTML或上万行节点代码作为最终Vue源码。先锁定common/project、目标画板、固定视口和页面状态；再获取完整基准图，并按系统框架、筛选区、主体列表、展开区、弹层和分页分区读取设计数据。

开始写代码前先输出公共组件复用清单、页面组件树、Mock数据结构、滚动缩放方式和拟修改文件。实现时复用TMS公共系统框架，重复内容必须数据驱动。完成后使用相同视口截图对比Pixso，并同时通过视觉、源码结构和npm run build验收。不要新增设计稿之外的内容，不要留下临时生成脚本、截图、差异图或导出JSON。
```

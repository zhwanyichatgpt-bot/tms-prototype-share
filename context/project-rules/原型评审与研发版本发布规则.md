# 原型评审与研发版本发布规则

本文是当前原型评审系统的产品口径，用于新对话、新工具和后续版本操作时快速恢复上下文。如早期讨论记录与本文冲突，以本文为准。

## 1. 版本与资料归属

1. 一个研发版本只归属“TMS 通用”或一个定制项目。
2. “需求归属”用于确定版本、讨论、PRD 和规则的业务上下文，不用于限制产品负责人可选的原型范围。
3. 创建或编辑版本时展示全部已注册原型，由产品负责人明确选择本次纳入页面。
4. 每个已注册原型必须说明原型归属、所属项目、对应需求或版本和用途备注，便于区分同名或相似页面。
5. 当前任务资料优先级为：当前研发版本 → 当前定制项目基线 → TMS 通用基线。

## 2. 研发看到的内容

1. 研发只通过对应版本的原型验证工作台进入。
2. 工作台目录中，“需求目录”与本次原型页面直接并列，不设单独“研发视图”，不设“本次原型”二级层级。
3. 业务页面是中央画布内容，不得创建 `WorkspaceShell` 等第二套原型验证工作台；若设计稿包含TMS业务系统顶部栏、工作台页签栏或左侧导航，这些属于被验证的业务系统框架，必须保留并优先使用通用业务组件实现。
4. 研发只看当前版本的需求概览、原型页面、原型标注和修改记录；不展示 PRD 清单、规则文件、讨论记录和产品内部待确认项。

## 3. 研发地址与完成标记

1. “生成研发地址”每个版本只能执行一次。
2. 地址固定为 `https://tms-prototype-share.netlify.app/review/{versionId}`。
3. 首次生成地址时形成“首次交付”；后续变更仍使用原地址，不重新生成。
4. 生成地址只代表本地版本记录已准备好，不代表 GitHub 已推送，也不代表 Netlify 已部署成功。
5. “标记完成”只表示该版本本轮工作完成，不代表业务上线，不冻结版本，也不影响后续变更。

## 4. 首次交付后的修改记录

1. 首次生成研发地址前的产品内部草稿调整不进入研发修改记录。
2. 首次交付后，对研发有影响的实际改动必须自动生成一批变更记录，不要求产品负责人在管理页手动重复填写。
3. 一组连续讨论并一次完成的关联修改只记一批，不拆成多条机械记录。
4. 只记录用户已确认、代码已实现且验证通过的变化；不记录讨论想法、失败尝试和未落地方案。
5. 每批变更至少包含：修改原因、修改类型、影响页面、修改前、修改后、研发注意事项。
6. 对外只显示“首次交付”和“第N次变更”，不显示 `R0/R1/R2`；内部数据仍可用修订号保证顺序。
7. PRD、业务规则、原型行为或研发实现结果发生变化，属于业务变更；标注文案精简、编号与定位修复、来源隐藏、评审组件优化等属于工具层优化，不单独进入研发修改记录。
8. 同一业务变化引起的 PRD、原型和标注同步只形成一批修改记录，不能把标注更新再次记录为下一次变更。

## 5. 指定版本的发布流程

1. 外部发布必须由用户明确指定版本并确认，例如：“确认发布北港水运 1.0.3.4，只发布这个版本”。
2. 当存在多个版本时，“全部上线”或“发布”属于边界不清；执行前必须先列出具体版本名称和 ID，由用户确认。
3. 发布前必须确认：
   - 目标版本名称和 ID；
   - 本次纳入的页面、标注、版本数据和变更记录；
   - 必须同步的共享框架与依赖；
   - 明确排除的其他版本和无关改动；
   - 本版本的固定研发地址。
4. 先运行必要的确定性测试和本地构建，再精确暂存待发布文件。
5. 必须验证“暂存快照”本身可构建且依赖完整；不能只依赖脏工作区的构建结果。
6. 推送后等待 Netlify 部署结果，并验证目标版本路由、版本 JSON、变更 JSON 和标注 JSON 均可访问。
7. 只有远程验证通过后，才能对用户表述“已发布成功”。地址已生成但 Netlify 失败时，必须明确说明“地址已记录，部署未成功”。
8. 部署任务显示成功后，仍需等待单页应用完成版本数据渲染，再核对需求目录、当前变更、目标原型页面和标注内容；不能只看到空壳页面或构建绿灯就结束验收。

## 6. 共享原型与版本隔离

1. 版本页面清单只限制研发目录展示范围，并不会自动复制一份独立的页面源码。
2. 同一原型页面被多个版本引用时，修改该页面可能同时影响多个版本。修改前必须检查所有引用版本，必要时新建项目专属页面。
3. 发布时不能只选择业务页面，还必须包含它们实际依赖的共享组件和框架文件。

### 6.1 原型源码物理分层

1. 当前采用一个仓库内的通用基线和定制项目子目录；项目数量增加本身不触发拆仓，只有独立团队、独立权限或独立交付等条件出现时才单独评估。
2. 源码和资料的当前物理落点以 [产品架构与目录治理规范](./产品架构与目录治理规范.md) 为准：产品、共用端、通用与项目分别分类。
3. 页面存在明确父子关系时允许物理嵌套；父页面 sourcePaths 使用精确文件，不得覆盖子页面。
4. 本次历史资料与源码已按产品归属统一迁移。历史位置查询 migration/2026-09-12-产品架构整理/path-map.json，不再向旧平铺目录新增内容。

### 6.2 定制项目继承与依赖方向

1. 每次原型验证开始前必须锁定 `common / project`；定制项目必须明确 `projectId` 和所继承的通用版本或 `pending`。
2. 定制项目没有差异时直接引用通用页面，不复制一份项目源码。
3. 项目新增能力或覆盖通用页面时，建立项目专属页面并记录项目归属、来源通用页面或版本和差异用途，不得为了项目需求直接修改通用基线。
4. 项目之间不得直接引用源码；跨项目可复用能力必须先单独评估是否进入通用基线，再由各项目升级。
5. 页面新建、移动或复制后，必须同步维护 `src/page-registry.js` 和 `review/page-catalog.mjs`，保证运行时路径、源码范围和项目归属一致。
6. 在其他 TMS 工作区启动原型验证时，先读取当地项目规则；若没有更明确规则，以本节作为通用判断基准，不得默认写入通用资产。

### 6.3 版本工作台内的页面导航（强制）

1. 版本工作台内（当前路由 `/review/{versionId}/{pageKey}`）的列表、详情、返回和跨页面操作，必须保留当前 `versionId`，统一使用版本路由 `/review/{versionId}/{pageKey}` 跳转，不得直接写死普通 `/{pageKey}` 地址。
2. 目标页面必须属于当前版本 `pages` 清单；不属于当前版本的页面不得通过版本路由进入。
3. 跳转必须保留业务所需的 query 参数（如运单 `key`、页签 `tab`）；返回列表同样保留 `versionId`。
4. 普通原型工作台（无 `versionId`）下允许兼容普通页面路由 `/{pageKey}`。
5. 跨页面跳转统一使用 `src/review/prototype-navigation.mjs` 的 `openPrototypePage(router, route, pageKey, query)`，不得在业务页面中重复编写版本判断。

## 7. PRD—原型—标注闭环

1. 一次业务修改按“确认业务变化 → 更新 PRD / 规则 → 修改原型 → 同步当前版本标注 → 判断研发影响 → 生成修改记录 → 指定版本发布 → 线上验收”闭环。
2. PRD 修改后不能把新增文字全部复制成标注；必须结合实际原型和现有标注重新判断保持、修改、新增、合并或删除。
3. 原型已经修改但 PRD / 规则没有支持，或 PRD 已修改但原型未实现时，标记为证据冲突并停止该项发布，不自动选择一方作为事实。
4. 当前版本的版本化标注是研发交付依据；自动或人工同步不得覆盖其他版本，也不得把定制规则写入通用基线。
5. 同一页面状态优先保留少量关键业务主题；标注总数不设固定上限，最终以研发是否能快速扫读、是否存在重复和页面空间是否清晰为准。
6. 研发查看面板不展示来源路径；来源继续保留在标注数据和本地编辑能力中，用于产品与 AI 追溯。

## 8. 版本标注同步目标

1. 只有产品在版本管理页主动点击“同步标注”才触发同步；文件保存、PRD 修改和原型修改本身不自动写标注。
2. 点击按钮即授权本次局部同步，不再增加二次确认。
3. 系统只比较上次成功同步以来的差异，只处理变化片段直接影响的标注；禁止全页、全版本或全仓审查，也不展示无关标注的“保持”项。
4. 需要变化的标注直接按修改、新增、合并、删除写入当前版本；确实无需修改时只返回“本次无需修改”。
5. PRD / 业务规则与实际原型存在真实目标口径冲突时，整批不写入，并明确展示 PRD 口径、原型口径和冲突原因。
6. 成功同步或确认无需修改后保存本地差异基线；下次只比较该基线之后的变化。
7. 标注同步完成后再进入修改记录与发布流程；写入不得覆盖其他版本或公共标注。

## 9. 当前已知限制

以下能力尚未实现，后续不得当作现有能力承诺：

- 版本管理页与 GitHub / Netlify 的一键发布联动；
- 在管理页回显真实的 Netlify 构建与部署状态；
- 自动判断某个版本对应的全部精确代码文件；
- 每个已发布版本真正独立、不随主分支共享源码变化的静态快照；
- 区分“计划上线日期”和“实际上线日期”的独立字段。
- 生产服务器直接执行标注同步；当前同步能力只在本地产品管理环境开放。

# 托运单管理需求讨论

## 1. 讨论背景
用户希望围绕大宗 TMS 中的托运单管理能力进行 0-1 讨论，目标是建设货主发布托运单、承运商报价、货主确认方案、承运商创建运输计划执行的业务闭环。

本次讨论分两阶段推进：
1. 先围绕托运单本体讨论，不展开水运计划怎么创建。
2. 在托运单创建页基本收敛后，继续讨论货主侧托运单管理列表页。

同时强调：
- 先参考现有知识库中的多式联运和公路集装箱运输计划方案。
- 当前先沉淀托运单创建页、业务规则、状态流转和管理列表页。
- 后续再展开报价单、详情页等页面。

## 2. 托运单模块共识

### 2.1 模块定位
- 托运单是统一业务对象。
- 托运单用于表达货主运输需求，是报价和计划的上游对象。
- 托运单不是运单、不是运输计划、不是结算单。

### 2.2 业务类型
- 托运单创建入口先选业务类型。
- 业务类型分为：散杂货、集装箱。
- 不做一套完全统一的业务明细表单。

### 2.3 运输方式偏好
- 货主可以设置可报价运输方式：公路、水路、铁路、联运。
- 可报价运输方式支持多选。
- 优先偏好方式单选、非必填，仅表达偏好。
- 最终运输方式由承运商报价方案决定。

### 2.4 报价模式边界
- 不在托运单层限制承运商报价模式。
- 后续由承运商在报价单中选择整票报价或其他报价方式。

## 3. 散杂货托运单讨论结论

### 3.1 多装多卸必须支持
讨论中明确：
- 当前业务存在真实的多装多卸场景。
- 一票货可能有多个装货点、多个卸货点。
- 因此托运单必须保留节点链，不能退化为单起单终的简单需求单。

### 3.2 货品必须与节点绑定
- 散杂货场景下，货品和节点必须绑定。
- 不同装货点、不同卸货点可能对应不同货品或不同数量。
- 因此不适合只做全局货品区。

### 3.3 引入 Batch ID 机制
用户提供了较完整的规则思路，讨论后确认：
- 每条装货记录生成唯一 Batch ID。
- 卸货记录必须选择来源批次。
- 卸货下拉仅展示当前节点之前的装货批次。
- 选择来源批次后，系统带出并锁定货品名称、单价、包装方式、配载方式。
- 卸货仅录入本次卸货数量。

### 3.4 一对多卸货支持
- 同一卸货点如需卸来自不同装货点的同名货品，应拆分多行录入。
- 每行只关联一个来源批次。

### 3.5 配载方式统一
- 同一张散杂货托运单只允许一种配载方式。
- 首条装货记录确定后，全单锁定。

### 3.6 校验方式
- 行内实时校验：卸货数量不得超过来源批次剩余可卸数量。
- 提交校验：按 Batch ID 校验、按货品总量校验。
- 如修改/删除装货记录影响后续卸货逻辑，必须提示并阻止提交。

## 4. 集装箱托运单讨论结论

### 4.1 集装箱与散杂货分开建模
讨论明确：
- 集装箱业务与散杂货业务差异明显。
- 不适合强行共用一套业务明细表单。
- 统一对象下分散杂货、集装箱两个入口更合理。

### 4.2 集装箱节点语义与计划保持一致
为便于后续基于托运单创建集装箱运输计划，讨论确定：
- 集装箱托运单节点类型与现有集装箱运输计划保持一致。
- 节点类型包括：提空、提重、装货、卸货、还重、还空。

### 4.3 集装箱来源是关键字段
讨论中围绕“货主提供箱子”和“承运商提供箱子”场景反复确认，最终达成：
- 集装箱来源必须作为需求字段保留。
- 可选值：货主提供、承运商提供。

### 4.4 箱源影响录入边界
- 货主提供箱子：货主通常知道完整交接链路，可录入完整节点链。
- 承运商提供箱子：货主通常只知道装货点、卸货点与箱需求。
- 承运商提供箱子场景下，托运单默认只要求录入装货、卸货节点。
- 如货主明确知道提还箱点，也允许补充录入，不强限制。

### 4.5 箱信息不与节点绑定
讨论后确认：
- 集装箱信息按整票维护。
- 不做节点级箱分配。
- 箱信息字段以箱型、数量为核心，其他如货品名称、预估重量、包装方式、备注作为补充。

## 5. 创建页字段与交互共识

### 5.1 联系人信息非必填
- 托运主体联系人、联系电话非必填。
- 节点联系人、联系电话非必填。
- 原因：真实业务中，发单时现场联系人未必已明确。

### 5.2 发布范围
- 发布范围单选。
- 候选值：全平台公开、指定平台可见、指定承运商可见。
- 不做“指定平台 + 指定承运商”混合组合，避免解释歧义。

### 5.3 保存草稿与提交发布
- 保存草稿允许不做完整业务校验。
- 提交发布必须走完整业务校验。

## 6. 状态流转讨论结论
用户提供了历史状态规则，讨论后进行统一收敛。

### 6.1 最终主状态
- 草稿
- 待审核
- 待确定
- 竞价中
- 待执行
- 执行中
- 已完成
- 已取消
- 已终止

### 6.2 命名调整
- 历史规则中的“已执行”调整为“执行中”，避免与“已完成”语义冲突。
- “启动”建议改为“恢复”，表达终止后恢复更准确。

### 6.3 公开托运单链路
- 草稿 → 待审核 → 竞价中 → 待执行 → 执行中 → 已完成
- 若平台无需审核，则草稿后直接进入竞价中。

### 6.4 指定托运单链路
- 草稿 → 待确定 → 待执行 → 执行中 → 已完成

### 6.5 异常链路
- 待审核 / 待确定 / 竞价中 可进入已取消。
- 待执行 / 执行中 可进入已终止。
- 已终止可恢复到终止前状态。

### 6.6 原因字段
建议为：
- 已取消增加取消原因。
- 已终止增加终止原因。

## 7. 管理列表页讨论结论
在创建页与状态流转收敛后，继续讨论了货主侧托运单管理列表页。

### 7.1 页面定位
- 管理列表页是货主侧的托运单管理工作台。
- 用于查看当前企业下托运单列表和不同状态托运单。
- 用于快速搜索、筛选、继续处理托运单。

### 7.2 页面结构
讨论后确认：
- 保留状态页签
- 保留搜索筛选区
- 保留新建托运单入口
- 保留列表区和分页区
- 不做统计卡片

### 7.3 状态页签
最终确定页签为：
- 全部
- 草稿
- 待审核
- 待确定
- 竞价中
- 待执行
- 执行中
- 已完成
- 已终止
- 已取消

### 7.4 搜索区字段
最终保留：
- 关键词（托运单编号 / 标题 / 货品名称）
- 承运商 / 物流服务商
- 业务类型
- 发布方式
- 创建人
- 创建时间
- 报价截止时间

明确去掉：
- 业务员字段

### 7.5 列表字段
最终收敛为 8 列：
1. 托运单
2. 运输信息
3. 承运商 / 物流服务商
4. 货品 / 箱信息
5. 报价信息
6. 状态
7. 备注
8. 操作

### 7.6 字段展示口径
#### 托运单列
- 展示托运单编号。
- 同时展示标签：业务类型（散杂货 / 集装箱）、发布方式（公开托运单 / 指定托运单）。

#### 运输信息列
- 展示首装地（X装）→ 末卸地（Y卸）摘要。
- 第二行展示装货时间、卸货时间。
- 时间口径为：首个装货节点时间、最后一个卸货节点时间。

#### 承运商 / 物流服务商列
- 竞价中状态展示“报价中”。
- 待确定展示指定承运商。
- 待执行、执行中、已完成展示中选承运商。

#### 货品 / 箱信息列
- 散杂货展示主货品 + 总量。
- 集装箱展示箱型箱量摘要。

#### 报价信息列
- 不再沿用旧稿“运输单价”口径。
- 统一改为按状态展示：待发布、待审核、待承运商确认、暂无报价/已报价X家、已确认方案、已创建计划等摘要信息。

#### 备注列
- 保留。
- 展示托运单创建时填写的备注内容。
- 不做内外备注摘要拆分。

#### 操作列
- 最多平铺展示 3 个按钮。
- 超出操作收纳到“更多”。
- 详情保留独立按钮。

# 承运企业社会运力采购与运力竞价闭环

## 1. 讨论背景

货主 A 将运输业务委托给承运企业 B。B 接受委托并形成托运订单、运输计划后，可能因自有运力不足，需要把部分或全部待执行运量投放到社会公共市场，由其他承运企业报价并承担实际运输，由此产生实际承运企业 C。

本次讨论的核心不是简单增加一次公开发布，而是解决以下问题：

- 如何让 B 清晰地采购社会运力；
- 如何避免形成 B→C→D→E 的无限多级托运订单；
- 如何复用现有“调度记录—运输任务—指派任务—运输执行”链路；
- 如何让货源大厅同时承载货源竞价与运力竞价，但不让用户混淆；
- 如何以原型向领导和业务人员验证方案是否容易理解。

## 2. 当前系统现状

1. 货主发布公开托运单后，承运企业在货源大厅竞价；中选后生成托运订单。
2. 承运企业基于托运订单创建运输计划。
3. 运输计划进入调度中心后，形成调度记录；下游企业接收运输任务，运输任务下可继续形成指派任务并组织实际执行。
4. 系统已有把计划发布到第三方运力平台寻找运力的能力。
5. 货源大厅同时在门户端和小程序端展示，原来主要服务公开托运单。

## 3. 核心问题

### 3.1 是否建立多级托运订单

早期设想是 B 再向 C 发起托运，C 还可以继续向 D 发起托运。这会造成托运订单、运输计划、价格和结算关系不断增加，且 C 可能同时收到托运订单和运输任务，用户难以判断应从哪个对象开始工作。

最终决定不采用无限延伸的多级托运订单模型。

### 3.2 运力采购从哪里发起

曾讨论新增独立“运力采购任务”单据、从托运订单直接发起、通过项目容器归集后发布，以及从运输计划发起。综合现有系统职责与用户路径，最终选择“从运输计划发起”。

### 3.3 货源大厅如何定位

货源大厅应被定义为统一的公开市场入口，而不是公开托运单的专属页面。不同来源的业务需求可以进入同一个大厅展示和收集报价，但中选后的后台处理仍回到各自的业务链路。

## 4. 方案演进与取舍

### 4.1 放弃：递归多级托运

- C 中选后再生成托运订单与运输计划，仍可继续发布给 D。
- 问题：层级不可控、对象重复、价格权限复杂、结算关系加长、用户操作路径不一致。
- 结论：明确排除。

### 4.2 放弃：新增独立运力采购应用或核心业务单据

- 独立对象虽然便于管理发布、报价和中选，但会增加应用入口与用户理解成本。
- 当前流程可以由运输计划、货源大厅和调度记录完成闭环。
- 结论：第一阶段不新增独立应用，也不让用户额外管理新的核心业务单据。

### 4.3 放弃：项目容器作为必经入口

- 项目容器适合汇总多订单、多计划和总体运量，但会增加用户理解成本。
- 单个托运订单本身可以拆分为公路、水路或多式联运等多个运输计划，因此计划已经能够承载不同运输组织方式。
- 结论：本次方案不依赖项目容器。

### 4.4 采用：运输计划发起运力竞价

- B 在已有运输计划上发布社会运力需求。
- 运输计划负责发起、查看报价和确认中选。
- 货源大厅负责公开展示和收集报价，不承担后台履约管理。
- 中选后直接衔接现有调度与运输任务链路。

## 5. 讨论结论

### 5.1 产品模型

- ✅ 角色稳定为三层：货主、合同承运商、实际承运商。
- ✅ B 是对货主承担合同责任的承运商；C 是 B 采购的实际承运商。
- ✅ C 不通过本功能继续向 D、E 发布，避免形成递归托运链。
- ✅ 不为 C 额外生成新的托运订单和运输计划，避免其同时面对托运订单与运输任务。

### 5.2 双竞价入口

- ✅ “货源竞价”：来源是公开托运单，中选后生成托运订单，承运企业再创建运输计划。
- ✅ “运力竞价”：来源是已有运输计划，中选后生成正式调度记录，并向中选企业下达运输任务。
- ✅ 两类需求都可进入货源大厅，但必须通过业务类型标识和页面入口区分。
- ✅ 承运企业看到的是可参与报价的业务需求，不需要理解后台来源单据的技术分类。

### 5.3 运力竞价主流程

1. B 已取得托运订单并创建运输计划。
2. B 在运输计划上选择“运力竞价”。
3. B 确认待发布的运输节点、货品及本次发布运量。
4. B 在“自有货源大厅”和“第三方运力平台”中选择一个发布渠道。
5. 选择自有货源大厅时，需求进入货源大厅，承运企业参与运力竞价。
6. 报价截止后，B 从有效报价中选择一家承运企业 C。
7. 系统直接生成正式调度记录，不增加“待下达调度记录”等现状不存在的中间状态。
8. 系统向 C 生成运输任务，后续沿用现有指派与运输执行流程。
9. 执行结果回到原运输计划，形成业务闭环。

### 5.4 中选与报价原则

- ✅ 一次运力竞价只中选一家承运企业，不支持拆分中选多个承运商。
- ✅ 中选动作与正式调度记录建立关联。
- 🟡 所有承运商的报价方案应作为本次竞价过程记录保留，中选报价作为调度结果依据；具体展示权限在 PRD 阶段明确。
- ✅ 不新增“待下达调度记录”状态。

### 5.5 发布渠道

- ✅ 发布渠道互斥，只能选择一种：自有货源大厅或第三方运力平台。
- ✅ 选择自有货源大厅时，走本平台的运力竞价、报价和中选流程。
- ✅ 选择第三方运力平台时，复用现有第三方平台发布与选运力能力。
- ✅ 两种渠道在同一个发布入口中配置，不拆成两个独立功能。

## 6. 货源大厅定位与用户表达

### 6.1 类型名称

- ✅ 公开托运单进入大厅后称为“货源竞价”。
- ✅ 运输计划发布的社会运力需求称为“运力竞价”。
- ✅ 不使用“运输分包”“乙方的乙方”等容易引起角色压力或误解的名称。

### 6.2 移动端入口

- ✅ 面向运力企业的移动端首页以货源大厅为核心，不再增加过多入口层级。
- ✅ 首页可直接在“货源竞价”和“运力竞价”之间切换。
- ✅ 扫码接单保留为右上角快捷图标。
- ✅ 卡片只展示判断是否参与报价所必需的信息，不展示“中选后生成什么单据”“下一步做什么”等后台流程说明。

### 6.3 详情与报价页

- ✅ 两类竞价详情页复用既有货源详情的地图、路线、节点卡片和整体视觉结构。
- ✅ 详情页主按钮统一表达为“参与竞价”。
- ✅ 本期只验证散杂货，不扩展集装箱报价。
- ✅ 货源竞价报价侧重运输方案与费用报价；运力竞价报价以实际承运报价为核心。
- ✅ 企业信息由当前登录企业带出，联系人和联系电话由报价人填写。
- ✅ 报价说明默认展开；运力报价包含计费依据与运输单价。

## 7. Web 端原型结论

### 7.1 运输计划列表

- ✅ 在单个运输计划的操作区域增加“运力竞价”入口。
- ✅ 原型工作台框架、顶部栏、目录和运输计划列表主体尽量按即时设计 1:1 还原。

### 7.2 发布运力需求抽屉

- ✅ 点击“运力竞价”后打开右侧抽屉，不使用居中弹窗。
- ✅ 页面优先复用即时设计中的“新增公开托运单-散杂货运输/新增托运单”结构、组件和视觉规范。
- ✅ 抽屉只保留三部分：运输信息、运费设置、偏好设置。
- ✅ 运输信息按装卸节点组织地址、时间、联系人、联系电话和货品表格。
- ✅ 本次发布运量直接在节点货品表格中填写，不再建立独立“运力设置”。
- ✅ 删除“是否允许货品混装”。
- ✅ 费用区直接复用设计稿的“运费设置”。
- ✅ 渠道、运输方式、可见范围、凭证和备注直接复用设计稿的“偏好设置”。
- ✅ 页面设计以复用为主，只替换业务字段和必要交互，不自行新增组件或重新排版。

## 8. 涉及对象与模块责任

| 对象或模块 | 本方案职责 |
|---|---|
| 托运订单 | B 与货主之间的承接结果；允许拆分创建多个运输计划 |
| 运输计划 | 运力竞价的发起、发布内容来源、报价确认入口和执行结果归集对象 |
| 货源大厅 | 展示货源竞价与运力竞价需求，供外部承运企业查看和报价 |
| 报价记录 | 保存承运企业报价信息，并关联原竞价与中选结果 |
| 正式调度记录 | 运力竞价中选后的调度结果 |
| 运输任务 | 下达给中选实际承运企业 C 的执行任务 |
| 指派任务 | C 在既有执行链路中组织车辆、船舶或司机的任务 |
| 第三方运力平台 | 与自有货源大厅互斥的外部运力获取渠道 |

## 9. 明确排除

- ✅ 不支持 C 继续向 D、E 递归发布运力竞价。
- ✅ 不新增运力采购应用。
- ✅ 不新增运力竞价单作为用户必须管理的核心业务单据。
- ✅ 不通过项目容器才能发起本流程。
- ✅ 不在中选后给 C 同时生成托运订单和运输任务。
- ✅ 不支持一次竞价中选多个承运商。
- ✅ 不新增“待下达调度记录”。
- ✅ 本期原型不处理集装箱运力竞价。

## 10. 待确认问题

以下内容属于后续 PRD 细化，不影响当前大流程和原型验证：

1. 🟡 报价截止前是否允许承运商修改报价，以及修改记录如何保留。
2. 🟡 中选后 C 无法履约时，调度记录、运输任务与竞价结果如何撤销或重新发布。
3. 🟡 中选价格在调度记录中的展示方式与价格查看权限。
4. 🟡 无人报价后的重新发布是复用原发布记录还是形成新的发布批次。
5. 🟡 运输计划列表最终需要展示哪些竞价状态。

## 11. 后续动作

1. 继续通过 Web 和移动端原型验证业务人员能否区分“货源竞价”与“运力竞价”。
2. 原型经用户和领导确认后，再将本次结论反哺到《运力竞价》PRD。
3. PRD 阶段补充状态、权限、异常、撤销与价格展示规则。

## 关键决策追溯

| 决策 | 结果 | 原因 |
|---|---|---|
| 是否支持无限多级托运 | 否 | 对象、价格、结算和用户路径会持续复杂化 |
| 运力竞价从哪里发起 | 运输计划 | 与现有调度和执行职责最接近 |
| 是否新增独立应用 | 否 | 现有运输计划、货源大厅和调度中心可以闭环 |
| 中选后给 C 什么对象 | 运输任务 | 避免托运订单与运输任务同时存在 |
| 中选生成什么调度对象 | 正式调度记录 | 复用现状，不引入不存在的待下达状态 |
| 是否允许多家中选 | 否 | 当前业务只需要一家实际承运商 |
| 发布渠道如何选择 | 自有大厅/第三方平台二选一 | 两种能力互斥，统一入口更容易理解 |
| 货源大厅如何定位 | 统一市场入口 | 支持不同来源需求展示和报价，但后台各走原业务链 |

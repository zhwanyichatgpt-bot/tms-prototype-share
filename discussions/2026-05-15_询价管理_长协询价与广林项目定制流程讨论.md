# 主题：长协询价与广林项目定制流程讨论

## 1. 讨论背景
- 客户新增长协询价场景：货主一次性发起多条线路的询价需求，由无车承运人拆分后发布到询价大厅，再由承运商逐条报价。
- 该场景与现有托运单、指定托运单、竞价大厅能力有关，但链路更偏“批次询价 → 线路拆分 → 大厅报价 → 货主确认 → 指定托运单”。
- 本轮讨论的目标是先把业务边界、单据粒度、角色分工、定制化范围定清楚，再沉淀 PRD 与原型验证输入包。

## 2. 当前现状
- 现有系统已有托运单、指定托运单和竞价大厅。
- 旧流程更偏向：货主指定托运单 → 无车承运人确认 → 创建运输计划 → 发布到大厅竞价 → 调度承运商。
- 新场景中，货主会一次性提交多条长协线路，且承运商一次只看单条线路、单条报价。
- 场景已确认属于**广林项目定制需求**，不应直接与通用需求混写。

## 3. 核心问题
- 长协询价应该以“批次”还是“单条线路”为核心对象。
- 无车承运人接到货主询价后，如何转成大厅发布单。
- 承运商是一次看全部线路报价，还是按单线路逐条报价。
- 货主确认后，托运单是一单覆盖所有线路，还是一条线路一张托运单。
- 货主创建时是否支持导入线路，批次内是否允许重复线路。

## 4. 讨论过程
- 最初讨论中曾考虑“询价单 → 大厅发布单”的父子关系，后来进一步明确为：**货主侧保留长协询价批次，无车承运人侧按线路拆分生成大厅发布单**。
- 对承运商侧的展示范围进一步收敛为：**一次只看一条线路，只对单线路报价**，避免整批统一报价。
- 对货主确认粒度进一步确认：**支持按线路部分确认**，未确认线路可继续流转。
- 对后续履约粒度进一步统一：**一条已确认线路生成一张指定托运单**，不做多线路合单。
- 对项目属性进一步明确：本需求应作为**广林项目定制能力**沉淀，PRD、AI 输入包和原型验证都要显式标注。

## 5. 讨论结论
- 结论1：长协询价按“批次”发起，按“线路”执行，线路是最小业务单元。
- 结论2：承运商端只看单条线路，只做单线路报价，不做批量统一报价。
- 结论3：货主支持批量导入线路，也支持手工新增线路；同批次内相同线路只保留一条。
- 结论4：无车承运人不能修改线路起点和终点，只能调整发布细节，如竞价时间、备注。
- 结论5：货主支持部分线路确认，确认后按线路生成指定托运单。
- 结论6：本需求明确归属为广林项目定制，不直接作为通用需求输出。

## 6. 涉及规则
- 线路导入模板字段：始发地、目的地、货品、货量。
- 同一批次内相同线路只能保留一条，且先判断是否同一货主。
- 无车承运人可调整的发布规则边界：竞价时间、备注。
- 承运商一次只看到一条线路，一条线路一条报价。
- 货主确认后，可直接基于确认线路创建指定托运单。
- 一条线路只对应一张指定托运单，不做多线路合单。

## 7. 涉及对象
- 业务对象：长协询价批次、线路询价明细、询价大厅发布单、承运商报价单、指定托运单。
- 涉及单据：货主询价批次单、无车承运人线路发布单、承运商报价单、货主确认单、指定托运单。
- 涉及状态：草稿、已提交、处理中、报价中、已选中、待货主确认、已确认、已关闭。
- 涉及字段：始发地、目的地、货品、货量、竞价时间、备注、报价金额、确认价。

## 9. 待确认问题
- 是否需要在后续原型里把“批次主单”和“线路明细”做成分层页面结构。
- 指定托运单生成后，是否还需要支持批量发起后续动作。
- 若同一批次内存在看似相同但时间窗不同的线路，是否仍按不同线路处理。

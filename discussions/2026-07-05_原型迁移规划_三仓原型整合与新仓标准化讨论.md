# 原型迁移规划：三仓原型整合与新仓标准化

## 1. 讨论背景

TMS 3.0 原型资产当前散落在三处代码仓，且三处技术栈、目录结构、运行方式都不一致：

- **TMS3.0功能记录/AI输出/原型验证/**：早期 HTML 单页原型 + hub 服务（3456 端口）托管
- **TMS3.0原型主仓/app/pages/**：Vue2 + z1-design 公司组件库 + 统一底座运行时
- **TMS3.0原型验证**（当前新仓）：Vue 3 + Vite + Element Plus，PM 工作流已初始化，`prototype/` 为空

新仓已迁移完整 PRD（13 份）与业务规则（7 篇），但原型产物一条未迁。本次讨论目标是：以新仓为标准，把另外两仓的原型验证内容整合迁移过来，统一技术栈与目录约定。

## 2. 当前现状

### 三仓技术形态对照

| 维度 | 功能记录仓 | 原型主仓 | 当前新仓（标准）|
|------|----------|---------|--------------|
| 技术栈 | HTML 单页 + 2 个 server.js + 1 个 Vue2 工程 | Vue2 + z1-design 公司组件库 | Vue 3 + Vite + Element Plus |
| 运行方式 | hub 服务 3456 端口托管静态页 | 统一底座 `npm run serve --page` | `npm run dev`（5173）|
| 目录约定 | `<模块>/<页面>/current/page.html` | `<域>/<页面>/current/src/App.vue` | 待定 |
| 数据 | 每页 mock-data.json | 每页 mock-data.js | 待定 |
| 标注 | 部分有 spec.yaml | 全量 spec.yaml v2~v7 | 本次不迁 |

### 已有原型盘点结论

- 13 份 PRD 中 **11 份已有原型**，2 份无原型（运输余量、一单制凭证）—— 这 2 份本质是跨模块业务规则，不需要单页原型承载。
- 主仓版本更新，**主仓有的优先取主仓**；主仓没有的取功能记录仓。
- 主仓另有 4 个无 PRD 对应的页面（order-manage、app-directory、prototype-annotation-platform、scenario/public-waybill-to-multimodal）。

## 3. 核心问题

1. 三仓代码不一致，如何以新仓为标准做框架迁移（非文件拷贝）？
2. 迁移范围如何取舍？
3. 已有原型标注是否迁移？
4. 是否需要用最新 PRD skills 重新梳理 PRD？
5. 原型在新仓里的目录约定、访问方式、页面间联动如何处理？

## 4. 讨论过程

- 提出三种原型对接方式（迁移源码 / 只建索引 / 挑选部分 / 只盘点）→ 收敛到「迁移原型源码进当前仓」
- 讨论"以新仓为标准"的真实含义：不是文件拷贝，是框架迁移/重写（HTML/z1 Vue2 → Vue3 + Element Plus），但界面样式、字段、交互、布局必须 1:1 还原
- 讨论 PRD 重写时机：先重写会拖慢迁移且与"界面不变"打架；最终定为先审查 PRD 再迁，迁完后再用 prototype-annotation 反哺
- 讨论原型目录约定：按 AGENTS.md 项目规则放 `prototype/`，每页一个子目录
- 讨论页面访问方式：总入口 + 动态 import() 加载，而非 vue-router
- 讨论页面间联动：因用户不熟悉技术方案，由 AI 推荐 Vue reactive store
- 讨论迁移批次：按模块分 4 批，每批迁完用户验证后再进下一批

## 5. 讨论结论（按确认态标注）

✅ **目录约定**：原型放 `prototype/<模块>/<页面>/` 下，每页含 App.vue + mock.js + notes.md

✅ **推进方式**：按模块分 4 批，每批迁完用户验证后再进下一批

✅ **迁移范围**：只迁有 PRD 对应的 11 个页面；无 PRD 的（order-manage、app-directory、annotation-platform、scenario）不迁

✅ **标注处理**：全部不迁，后续重新走 prototype-annotation

✅ **页面访问**：总入口（`src/App.vue`）+ 动态 `import()` 加载 `prototype/<页>/App.vue`

✅ **页面间联动**：采用 Vue 模块级 reactive store（轻量级，不必上 pinia，一个 `reactive({...})` + 几个 setter）。理由：刷新=回到初始 mock 状态更干净，无需 localStorage API，代码更短

✅ **PRD 处理**：先审查 PRD 再迁。审查 ≠ 重写，仅发现实质问题时才修订

✅ **迁移工作流顺序**：阶段 0 框架准备 → 阶段 1 PRD 审查 → 阶段 2 分批迁移 → 阶段 3 交付

## 6. 涉及规则

- AGENTS.md「PM 工作流配置」：原型目录为 `prototype/`，组件库为 Element Plus，端口 5173
- AGENTS.md「Restraint」：只做被要求的事，需求没提的视觉效果/交互/字段/组件一律不加 → 迁移必须 1:1 还原，不得自行增强
- AGENTS.md「Verify-Before-Claim」：声称"完成/构建通过/能跑"前必须实际运行 `npm run build` 或 dev server
- AGENTS.md「Handoff-Guided」：每步完成只提示下一步，用户拍板才进入下一环
- 业务规则目录 `context/business-rules/`：PRD 审查时需对齐统一术语与字段口径

## 💡 关键决策追溯

- **为什么用 Vue reactive store 而非 localStorage**：用户表示不熟悉技术方案，由 AI 推荐后用户接受。理由是原型验证场景下"刷新=回到初始 mock 状态"更干净，且代码更短、无需 localStorage API。
- **为什么先审查 PRD 再迁**：用户最初问"是否需要用最新 PRD skills 重新梳理 PRD"，AI 判断不需要重写但建议审查。用户最终选择"先审查 PRD 再迁"，确保迁移基于经过体检的 PRD 源头。
- **为什么按模块分 4 批**：11 页面工作量较大，分批可中断、可验证，避免一次到位的风险。
- **为什么主仓版本优先**：主仓是 Vue 工程、有 spec 标注、更新时间更晚（5-30~6-21 vs 4-8~5-30），成熟度更高。

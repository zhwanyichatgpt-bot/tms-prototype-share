# 至简智运货主端：资金流、费用、结算与开票（D01）

## 1. 讨论背景

- 2026-09-16 评审后梳理出 D01–D08 八项产品设计问题，本轮优先讨论 D01（资金流、费用、结算与开票），产出"费用形成 → 结算 → 付款 → 开票"业务链路及各方操作分工。
- 讨论基于至简智运货主端既有原型（结算与付款二级页、我的页钱包入口）与 PRD R13/R16 规则展开。

## 2. 当前现状

- 货主端结算页已有"待结算 / 待付款"双页签，展示所属平台、实际收款方、付款截止，但无费用构成、无钱包联动、无开票能力。
- 平台内部结算状态机为"待审核 → 待打款 → 已打款"，由外部 OA 驱动（见多式联运货主结算 PRD），货主端此前未定义与该状态机的关系。
- 支付已与平安银行完成渠道对接。
- 产品架构文档原表述"使用第三方车辆与交由第三方网货平台承接不是同一模式，需区分承接、执行和结算主体"，本轮经用户修正。

## 3. 核心问题

1. 货主向谁付款，页面上谁是收款方？
2. 货主支付的金额包含哪些费用？信息服务费是否在货主侧体现？
3. 一票货多平台承接时结算单如何生成？能否合并付款？
4. 平台内部"复核、核算、申请打款、打款"与货主操作如何区分？
5. 运输发票和信息服务费发票分别由谁开给谁？
6. 钱包在链路中承担什么作用？

## 4. 讨论过程

- 初始讨论按"自营承接 + 第三方聚合"双模式推导资金链；用户修正为**智运只做聚合，货主与承接平台直接发生资金关系**，双模式分叉塌缩为单模式。
- 用户提供平安银行资金流程图，明确三条平行资金流：货主→平台（运费，经平安结算通）、平台→智运（技术服务费，预充值按笔扣除）、平台→区域代理人（居间费，智运不碰钱）。
- 服务费向平台收取，因此货主侧零体现，行情页比价口径不受影响（此前的潜在冲突消失）。
- 发票流程用户定为：货主选货源 → 带出货源下关联结算单 → 申请开票 → 平台审核 → 平台开具电子发票。由此反推结算单粒度，用户确认方案 A：**结算单按「货源 × 平台」生成**，一票货源在每个承接平台各一张结算单，无需部分开票。
- 付款模式用户确认为"充值独立"：货主先充值进钱包余额，付款时从余额扣，钱包成为支付主链路必经环节。
- 评审 Pixso 开票设计稿（16 个画板）后进入开发；设计稿主干可用，但混有开票方视角页面（"上传电子发票"）与两轨状态机（等待审核 / 等待平台校验），开发时按货主视角收敛。

## 5. 讨论结论

- ✅ 至简智运为纯聚合方：不赚运费差价、运费资金不过智运账户；至简智运本身也是承接平台之一（原型演示用，可换名）。
- ✅ 收款方显示承接平台的结算主体全称，不显示平台品牌名。
- ✅ 货主应付 = 运费，不含任何服务费；技术服务费由智运向承接平台收取并开票给平台，货主全程不可见。
- ✅ 结算单按「货源 × 平台」粒度生成；金额未形成时不生成数值（沿用 R13"未知不得写 0 元"）。
- ✅ 平台内部"核算 → 复核 → 申请打款 → 打款"对货主不可见；货主端只有三个状态：待结算、待付款、已完成。两套状态机是同一业务对象的两个角色视图，不是同一状态机。
- ✅ 付款采用"充值独立"模式：货主在平安银行开户 → 充值进钱包余额 → 余额支付。钱包为核心页面（余额、充值、提现、流水）；提现必须保留。
- ✅ 货主端账户层级只有两个：绑定的银行账户（充值来源/提现去向）与钱包余额；"平安结算通待分配账户"等银行侧概念不出现在货主端。
- ✅ 付款状态建议三态：待付款 → 处理中（已发起，等待平台确认）→ 已完成，对应"平台需授权支付运费"的时间差。
- ✅ 允许勾选多张账单批量付款，但每笔独立交易、独立收款方、独立开票；多平台合并一笔付款仍然禁止（不破 R16）。
- ✅ 开票：仅已付款的结算单可申请（先款后票）；本轮仅电子发票；不做部分开票；一张结算单对应一张发票。
- ✅ 开票流程：货主选货源 → 带出该货源下关联结算单 → 申请开票 → 平台审核 → 平台开票 → 货主下载发票。
- ✅ 货主端开票状态统一四态同轨：待开票 → 开票中 → 已开票 / 已驳回（可重新申请）；"平台审核""发票校验"收敛进"开票中"黑盒。
- ✅ 企业抬头必填仅企业名称 + 纳税人识别号 + 收票邮箱（增值税普票口径）；注册地址/电话/开户行/账号为专票字段，选填。
- 🟡 余额不足时批量付款的行为（整单付不了还是逐个付到不够为止）待定。
- 🟡 小简余额预判（"还差 ¥12,600，建议先充值"）是否纳入本轮待定。

## 6. 涉及规则

- 承接规则：货主与承接平台直接建立合同与资金关系，智运不经手运费资金（无二清）。
- 结算单生成规则：按「货源 × 平台」生成，一票货源在每个承接平台各一张。
- 先款后票规则：仅已付款结算单可申请开票。
- 状态映射规则：平台内部账务状态与货主端三态（待结算/待付款/已完成）映射展示，不混用。
- 钱包规则：充值独立、余额支付、可提现；货主端不出现银行侧账户名词。
- 开票状态规则：待开票 → 开票中 → 已开票 / 已驳回，四态同轨，驳回后可重新申请。

## 7. 涉及对象与影响范围

- 业务对象：货源计划、结算单（货源×平台）、付款账单、钱包余额、开票申请、发票。
- 涉及页面：结算与付款页（费用构成、批量付款待扩展）、我的页（发票管理入口已上线）、发票管理（申请开票 / 开票记录 / 开票详情，原型已完成）、钱包（待设计）。
- 外部依赖：平安银行支付渠道（已对接）；各承接平台开票接口（每家需单独接入，智运只转达申请，自营部分内部闭环）。

## 8. 待确认问题

- 余额不足时批量付款的截断行为。
- 计重口径（装货/卸货）——决定待结算金额何时形成，属财务规则，不影响本轮结构。
- 小简余额预判是否纳入本轮。
- 钱包页面设计（余额、充值、提现、流水）尚未开始。

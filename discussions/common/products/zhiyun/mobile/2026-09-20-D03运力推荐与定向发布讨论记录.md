# D03 运力推荐、详情与定向发布讨论记录

> 2026-09-29 局部替代：首页推荐已确认仅展示个体司机，不再混排车队/物流企业；卡片改用车辆图片、合作角标、来源标签、整体准时率与推荐百分比。首次推荐不联动本次发货表单、新用户可随机展示。最新规则见[本次收口记录](2026-09-29-首页推荐与发布字段讨论收口.md)和[首页PRD](../../../../../prd/common/products/zhiyun/mobile/至简智运货主端-首页-PRD-v1.md)。下文车队混选保留为历史与其他入口证据，不再作为首页混排要求；定向是邀请、来源分层等未被替代的结论继续有效。

本记录承接[货主端评审待办与讨论进度](至简智运货主端-评审待办与讨论进度.md)的 D03/T03，覆盖首页推荐运力的两类主体：**物流企业（车队）**与**个体零散司机**。2026-09-20 讨论车队，2026-09-21 讨论个体司机。

## 1. 讨论背景与目标

货主在至简智运首页浏览推荐运力时，**尚未填写本次货源**。货主希望先判断某支车队或某位司机是否适合运输，再向其发布货源。本记录聚焦首页推荐运力、运力详情以及由详情发起的定向发布；发布页的完整交互和跨平台接入方式仍需继续设计。

2026-09-20 使用 Pixso 中既有船舶详情画板 `1:7107` 参考信息层级和移动端样式；公路运力信息需按实际业务重新组织，不照搬船舶位置或联系场景。

## 2. 已确认的业务方向

### 2.1 定向对象与承接机制

- ✅ **定向对象为车队或个体司机，两者可混选。**不要求货主指定车队内的某位司机，也不走车队将货源逐车指派的流程。
- ✅ **定向发布后的承接是「邀请」，不是「派单」。**被指定的车队成员或个体司机在各自货源大厅看到该货源并**自主决定是否接单**；非指定对象不应看到或承接。车队与个体司机共用同一套承接逻辑，不另立规则。
- ✅ **支持指定多个对象。**可指定多支车队、多位个体司机，不预先分配承接量，也不设置单对象的承接额度；各主体在同一货源总量和剩余量范围内承接。总量并发控制、已接单部分和剩余量的跨平台口径与 D04 联动讨论。
- ✅ **可加为常用。**车队可关注、个体司机可加为常用司机；二者**合并为同一份名单「我的运力」**，货主只维护一份名单，发布时在同一处选择。
- ✅ **详情发生在发布货源之前。**首页推荐运力进入详情，货主在详情判断是否合适；详情的主要操作指向填写并发布本次货源。已有货源发布后再选择承运商是另一入口，后续需与本入口对齐。
- ✅ **推荐匹配度与服务评分分开。**首页的推荐百分比表达推荐排序，详情中的履约评价表达服务质量；不能将二者互换或重复当成同一指标。
- ✅ **分配时机不变。**指定车队或司机后由承接方自主抢单，本场景不做平台侧派单。

### 2.2 个体司机作为独立业务对象

- ✅ **个体司机详情页不套用车队那套。**个体司机是实际承运人（人 + 一台车），没有组织背书；页面**不出现企业资质**（营业执照、道路运输经营许可证）、**不出现规模与人数**、**不出现企业主体核验**。
- ✅ **不显示「当前是否空闲」。**货运提前期是天级，「此刻空闲」与「装货日空闲」不相关；显示出来会被货主读成承诺，属于误导而非信息不足。应对「司机不接」的机制是**多选**（多选几位，谁先接算谁的），不是预测单个司机的可用性。
- ✅ **不列证照明细**（身份证实名、驾驶证、从业资格证、行驶证、车牌）。认证只保留一个作用——**说明数据来自哪个平台**。
- ✅ **不引入五分制评分（如 4.8 分）。**会成为同屏的第三个百分比；履约指标本身就是服务评价；且评分口径（谁打分、样本量、周期）尚未定义。

## 3. 车队详情：复盘与设计倾向

当前原型已增加车队详情、评分、线路、车型规模、履约、资质和固定操作栏，但仍在评审中，未得到页面方案认可。

| 当前问题 | 🟡倾向处理 |
|---|---|
| 名称下的摘要重复线路、货品卡内容 | 删除摘要，线路与货品在运输能力区集中呈现 |
| 顶部车辆/司机数量与下方车型构成分散 | 归入同一“车型与规模”区：总规模与构成只展示一轮 |
| 顶部认证与下方资质重复 | 平台来源在主体区展示一次，认证及证照集中在资质区 |
| 顶部和底部分别展示同一个 4.8 服务评分 | 仅在顶部保留一次评分；履约区展示与评分不同的证据 |
| 来源平台在主体、履约说明及评分条中反复出现 | 主体区明确运力来源；有不同数据提供方时再就近说明 |
| 两点虚线的“公路运输”线路图信息少 | 以历史线路记录展示城市对、相关货品及有来源的承运记录；支持多条代表线路，不伪造实时轨迹或地图 |
| 字符拼成的状态栏图标及无实际操作的右上角胶囊 | 使用已有移动端资产或移除无意义装饰 |

🟡 **建议的信息顺序**：车队身份与唯一服务评分 → 运输能力（历史线路、货品、车型及规模）→ 合作履约 → 资质 → 底部关注与定向发布。每项内容要回答“是否适合本次运输、是否可信、下一步怎么做”，不为填满页面添加卡片。底部主按钮当前原型使用“定向发布”，最终文案随发布流程一起确认。

页面无需出现“原型示例”“待平台接入”等面向研发的说明；原型数据仍须在资料和代码中明确为 Mock，不能据此宣称平台已提供真实评分、证照或历史记录。服务评分的计算口径、统计周期、评价来源尚待确认；“常跑线路”也需要历史承运依据。无依据时不展示精确次数或实时运力。

## 4. 个体司机详情：设计与口径

### 4.1 为什么不能套用车队那套

| | 车队 | 个体司机 |
|---|---|---|
| 主体性质 | 承运商（组织） | 实际承运人（人 + 一台车） |
| 货主判断什么 | 组织靠不靠得住：规模、资质、履约稳定性 | 这台车这个人能不能干：车对不对、人跑得怎么样 |
| 承接方式 | 多个成员自主抢单 | 只有他一人，他没空就是没空 |
| 数据来源 | 车队自报 + 平台流水 | 基本只有平台流水，没有「组织」可言 |

### 4.2 竞品与监管依据

本轮经外部检索核对，来源可复核。

**竞品（货主端能看到司机的什么）**

| 平台 | 可见内容 |
|---|---|
| 货拉拉（订单详情页） | 头像、姓名、联系电话、车辆类型、车牌号 —— 无证照 |
| 福佑卡车（司机档案） | 姓名 + 省市（经纪人派单模式，货主不挑司机） |
| 满帮「找货车」列表 | 车长、车型、用车类型、装货时间、起止城市；筛选维度含车长分段与车型分类（面包车/冷藏车/平板/高栏/高地板/集装箱/保温/飞翼车/爬梯车/厢式）——**全是车辆条件，无人的信息** |

行业中没有把证照明细展示给货主的做法；能站住的运力信息只有两类——**车辆维度条件**，与**平台级的履约指标**。

**信用指标口径**

- 满帮对货主的信用体系：完单量、成交率、取消率、超时取消率、好评率、有责客诉率（五维度六指标）。
- 监管口径（《网络平台道路货物运输经营服务指南》）：围绕**运输效率、运输安全、服务质量、客户满意度**建立对实际承运人的信用评价体系，评价结果公示；诚信数据取**运单业务量、货主投诉占比、运输误点率、货损率、事故率**。
- 《网络货运承运平台经营管理办法》（交运规〔2026〕1号）第十七条：平台应当建立对实际承运人的服务评价体系，公示服务评价结果。

评分与履约指标**均无按线路拆分的先例**。

### 4.3 页面结构

🟡 信息顺序：**是谁的车 → 能干什么活 → 跑得怎么样 → 你和 TA → 底部操作**

**① 是谁的车**：头像、姓名、`运力来源 · {来源平台}`、推荐百分比（唯一一处）。

**② 能干什么活**：每项为「数据 + 结论」成对出现——只有结论是平台自说自话，只有数据是让货主自己算。描述口径**对齐发布货源时要填的字段**（货品、重量、车型、线路），避免交给货主换算。

- 常跑线路 · `福州 → 天津` **12 趟** —— 用趟数而非线路准时率
- 车型与载重 · `13米高栏 · 31吨`
- 实际承运过 · `煤炭、钢材` —— 是**跑过什么**，不是**声称能拉什么**

**③ 跑得怎么样**：与车队详情同一组指标、同一排版（三列）——`履约单` / `准时率` / `货主好评率`，下方附图「有责投诉」「货损记录」，有异常时转橙红。

**④ 你和 TA**：合作次数、最近一次合作时间，标注「本平台记录」。

**⑤ 底部固定**：`加为常用` + `定向发布货源`。

**列表卡片**：与车队卡片同一套标签词汇——`履约 N 单` / `准时率 N%` / `来源平台名`。

- ✅ **卡片只放事实，不放结论**（如「煤炭、钢材」而非「适合大宗散货」）。列表中五条多为大宗，结论无区分度，事实能让货主对上自己的货。
- ✅ **卡片标签与车队完全统一。**来源标签**不加「平台」二字**，直接写平台名。
- ✅ **卡片不出现司机评分。**同屏已有推荐百分比与准时率两个百分比，再加五分制评分会成为第三个。

### 4.4 关键指标口径

- ✅ **常跑线路带趟数。**趟数是计数，没有小样本噪音，且能把个体之间区分开——推荐本身按货主常跑线路推，只写线路名会导致所有卡片同值。
- ✅ **准时率用整体口径，不做线路维度。**线路维度样本量小时百分比剧烈跳动（2 趟晚 1 次即 50%）；竞品与监管均为平台级整体口径。
- ✅ **列表不显示「适合这趟」类结论。**详情发生在发布货源之前，货主尚未填写本次货源，「这趟」不存在。页面职责是摊开运力能干什么活，由货主自行对应。

### 4.5 数据来源分层

- 承运记录、履约指标、平台核验结果：**来自运力来源平台**，展示时标注来源。
- **「你和 TA 的合作」为本平台独有**。来源平台只知道司机在自身平台的表现，不知道他与哪个货主重复合作过。此为聚合方相对来源平台的差异价值，须单独呈现。
- 该分层同时解决新接入运力的问题：司机在本平台无历史，但在来源平台的记录可继续使用，不至于是一张白纸。

## 5. 期望的操作闭环与当前原型差距

🟡 **待设计的完整路径**：首页推荐运力 → 运力详情 → 定向发布并填写货源 → 确认指定对象（车队与个体司机可混选、无单对象份额）→ 发布成功并显示定向范围 → 被指定的车队成员或个体司机在货源大厅可见、自主接单 → 货主查看承接进度和剩余量。发布前后的权限、成员变化与接单校验需在对应承接平台支持下落地。

**当前实现状态（截至 2026-09-21）**：

- `FleetDetailPage.vue` 可进入车队详情并点击“定向发布”；`App.vue` 将所选车队带入 `QuickPublishFlow.vue` 的首步横幅。
- 个体司机已接入：`DriverDetailPage.vue` 可进入详情并点击“定向发布”，横幅按对象区分「已选择司机 / 已选择车队」。
- 但发布第二步仍默认“指定平台”并预选两个平台，**没有保留所选车队或司机作为最终定向对象**；成功页也未表达定向范围。因此当前原型仅完成入口衔接，**没有完成定向发布闭环**，不得将其作为已实现规则展示。

## 7. 适用边界与待确认

1. 🟡 发布页在哪里添加、移除并核对定向对象；如何同时表达「车队范围」与「单个司机」两种对象；平台选择与对象选择的关系如何呈现，需要与 D02 已确认的平台可用性规则对齐。
2. ⚪ 各承接平台是否能识别车队及其成员、能否识别被指定的个体司机，并在货源列表和接单时校验资格；不具备能力的平台如何提示或阻断，须逐个平台确认。原型阶段可用明确的 Mock 状态设计交互。
3. ⚪ 车队跨平台存在、成员退出或转队、发布后增减指定对象、接单瞬间资格变化等边界，需要定义可见性和已承接订单的处理。同一司机在多来源平台的重复计数与去重口径同样待定。
4. ⚪ 准时率中「提货误点」与「到货误点」是否分开统计。大宗货运迟到常因装货点排队或货主未备好货，混合统计会把责任错误归给司机；监管原文为「提货、到货的误点情况」，本身是两个节点。
5. ⚪ 线路记录、车队规模与履约指标的统计周期及更新频率。数据提供方已明确为运力来源平台（见 4.5），周期与频率仍待确认；这些信息与首页推荐百分比的口径要分开。
6. ⚪ 「我的运力」名单是否在「我的」下建独立管理入口。本轮合并了名单概念，未落地承载页面。
7. ⚪ 发布成功页是否展示定向范围（车队 + 司机）。
8. ⚪ 回程车／司机近期行程方向是否纳入。属另一个字段（当前行程 vs 历史记录），建议单独一轮，不与本记录混做。
9. ⚪ 底部主按钮文案在车队页与司机页是否统一使用「定向发布」。
10. ⚪ 一票货源的共享剩余量、并发接单、修改取消及运单形成归入 D04；本记录不提前替代 D04 规则。

- 货主明确提出指定车队，而非指定车队内的司机；指定后由车队成员在货源大厅自主承接，其他车队不可见。
- 货主明确提出可指定多个车队、不按车队限制货量，能接多少取决于货源剩余量。
- 货主明确指出浏览运力发生在填写本次货源之前，详情的主要价值是引导向该运力发布货源。
- 货主连续评审指出：评分与来源平台呈现不足、页面信息重复、状态栏占位字符和线路虚线不合适；现阶段应先梳理信息架构，再做视觉修补。
- 货主明确：可以选择多个司机；选中后该司机在货源大厅可见，接不接由他自己决定；同时可加为常用司机。
- 货主明确：「常用司机」与车队「关注」合并为一份名单；一次发布可混选车队与个体司机。
- 货主明确：能力展示要「列能力」与「给结论」两者兼有。
- 货主纠正：「能干这趟」的框架有误——详情发生在发布货源之前，应展示运力能干什么活。
- 货主纠正：「合作记录取不到」的判断有误，运单关联即可统计。
- 货主纠正：不能以「拿不到数据」作为不做功能的理由，产品应先判断该功能有无价值。
- 货主明确：列表卡片「准时率」「履约单数」应采用与车队一致的标签形式，来源标签不写「平台」二字。

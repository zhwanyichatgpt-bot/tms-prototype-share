# 通用定制隔离与研发版本管理

> 本文保留早期讨论过程，其中“已上线冻结”、“R0/R1 对外展示”和“重复发布研发地址”等早期表述已被后续验证结论替代。当前有效口径以 [原型评审与研发版本发布规则](../../../../context/project-rules/原型评审与研发版本发布规则.md) 为准。

## 1. 讨论背景

当前项目是一套面向 TMS 产品线的原型验证与评审系统。随着通用化需求、定制项目需求和研发交付批次持续增加，同一业务页面可能同时存在通用规则和多个项目规则。现有全量页面目录和平铺式文档存储容易造成：

- 产品讨论时混用通用规则与定制规则；
- AI 读取 PRD、业务规则和原型时串项目、串版本；
- 研发在工作台中看到与本次任务无关的页面和历史需求；
- 研发过程中的需求修改覆盖旧内容，无法说明本次与上次的差异。

## 2. 目标与总体方案

✅ 将项目升级为“长期产品基线 + 定制项目基线 + 研发交付版本”的三层结构。

1. **TMS 通用产品基线**：保存已上线、持续有效的通用 PRD、业务规则和原型能力。
2. **定制项目基线**：记录项目所继承的通用基线和项目专属覆盖，不反向污染通用资产。
3. **研发交付版本**：聚合一次已确定的需求范围、计划上线时间、本次原型、原型标注和修改记录，作为研发实际评审与开发入口。

## 3. 文档创建与归属规则

✅ 所有新讨论记录、PRD、业务规则和其他需求文档，从创建之初就必须区分“TMS 通用需求”或“定制项目需求”。

### 3.1 创建前置条件

1. 先确定需求归属为通用或定制。
2. 定制需求必须同时明确所属项目。
3. 再判断是否已归属某个研发交付版本。
4. 归属不明确时不得自行判断，不得先写入通用目录。

### 3.2 文档身份

新文档至少记录：需求归属、所属项目、研发版本和文档状态。早期讨论尚未进入研发版本时，研发版本可为 `pending`，但通用/定制归属不得缺失。

定制需求后续若认为具有通用价值，需要单独发起“定制能力转通用”评估，不得直接将原定制文档改为通用文档。

## 4. 研发版本定义与生命周期

✅ 一个研发版本代表一次产品已经确定的需求范围和计划上线时间，是合并交给研发的交付单位，不等于 TMS 全产品页面的大版本。

版本状态为：

1. 整理中；
2. 待研发评审；
3. 开发中；
4. 待上线；
5. 已上线（冻结）。

版本在研发评审、开发和测试过程中可以继续修改，只有真正研发上线后才冻结。已上线版本不得原地修改，新需求必须进入新版本。

## 5. 修订与修改记录

✅ 产品第一次正式交给研发评审时形成 `R0` 初始基线。`R0` 之前的产品内部草稿调整不进入研发修改记录。

`R0` 之后，所有对研发有影响的修改必须形成 `R1`、`R2` 等新修订批次，已交给研发的历史修订不得覆盖。

每个修订批次至少记录：

- 修改时间与修改原因；
- 影响模块和页面；
- 修改前与修改后；
- 对研发的影响和需要注意的实现点；
- 当前修订号和修改状态；
- 关联的原型位置。

一个修订批次可包含多个修改项，不将每个文案或细小调整拆成独立版本。

## 6. 研发评审展示边界

✅ 研发进入某个版本后，只查看该版本的：

- 版本概览；
- 本次原型目录和可交互原型；
- 原型标注；
- 修改记录。

研发不需要在评审工作台中查看 PRD 清单、业务规则文件、讨论记录、产品内部待确认内容或其他版本的原型。PRD 和业务规则仍作为产品与 AI 生成原型、原型标注的内部依据。

版本页面需要设置独立的“修改记录”信息区域，便于研发查看当前修订与上一次修订的差异。

## 7. 项目内部资产隔离

✅ 讨论记录、PRD、业务规则和原型需要按通用/定制项目分层存储。

当前版本任务的资料读取优先级为：

1. 当前研发交付版本；
2. 当前定制项目基线（定制需求时）；
3. TMS 通用产品基线。

通用需求只修改通用资产，定制需求只修改对应项目资产。本次版本默认只能读写版本清单纳入的文档和页面，其他版本内容默认只读。

## 8. 工作台目录规则

✅ 页面注册表记录项目拥有的全部原型资产，但不再直接决定研发看到的目录。

研发工作台必须根据当前版本清单生成目录，只展示本次交付纳入的页面。一个服务器可以通过不同版本路径保留多个交付版本，已上线冻结版本不被新版本覆盖。

## 9. 明确排除

- 📌 本期暂不设计原型标注中的“变更特殊提醒”；
- 📌 本讨论不直接确定版本编号格式、项目编码和 UI 视觉方案；
- 📌 不将 PRD 清单暴露给研发评审视图；
- 📌 不在方案未落地前批量移动或删除旧文档。

## 10. 待确认问题

- 版本编号、项目编码和修订号的具体命名规则；
- 现有讨论记录、PRD、业务规则和原型的分类、迁移与兼容策略；
- 定制项目能力转为通用基线时的评估和合并机制；
- 修改记录是否需要增加研发确认接收状态。

## 11. 后续动作

1. 更新项目基础规则，引入需求归属、版本上下文、修订记录和研发展示边界。
2. 设计并确认新的目录与版本数据结构。
3. 分别调整 `discussion`、`prd-manager-v2`、`prototype-validator` 和 `annotation` 工作流。
4. 实现版本管理、版本范围目录和修改记录展示。
5. 最后制定旧资料迁移方案，经确认后再执行迁移。
